## 已确认目标

第一版聊天资料导入同时覆盖：

1. 从聊天资料创建待人工确认的新工单草稿。
2. 向客服明确选择或匹配的已有工单增量补充资料。

管理端必须有两个清楚区分的入口：

1. **聊天记录整包导入**：接收微信导出的文件夹或 ZIP；完整聊天文字也可以通过粘贴或 TXT/PDF 提交。解析后自动生成消息时间线、字段候选、附件分类候选及冲突提示。
2. **逐项识别上传**：客服先选择资料分类，再上传单个 TXT、PDF、JPG/JPEG/PNG 文件或粘贴文字；系统按该分类提取候选信息并等待人工确认。

任何候选都不能直接覆盖正式字段，不能自动派单、批准报价、决定加价、确认核损、开放维修、记账或结算。确认写入时必须复用现有业务服务、版本、状态、权限、幂等和审计规则，禁止绕过状态机直接更新表。

## 已验证的 Windows 微信样本格式

用户在工作区外提供了一份真实导出文件夹。只允许用它理解格式，不得把文件、正文、手机号、车牌、地址、哈希或图片复制到仓库、测试、日志或提交中。应创建合成脱敏测试夹具。

已观察到的结构：

```text
聊天记录_YYYYMMDD_HHMMSS/
├─ 聊天记录.txt
└─ 聊天记录内的图片、视频和文件/
   ├─ 微信图片_时间_1.jpg
   └─ ...
```

TXT 以发送人、消息时间和正文为一组；附件消息使用类似 `[图片] 文件名.jpg` 的文本引用，能与子目录文件一一关联。解析器不能把导出目录名、发送人、聊天时间或无标签编号自动解释成正式案件字段。

## 图片与文字处理边界

- 图片作为聊天原始附件保存，不对图片执行 OCR，也不做基于像素的视觉识别。
- 整包入口依据图片前后的聊天文字、消息顺序、发送人和附件文件引用生成分类候选，并保存分类依据。没有足够上下文时标为待人工分类。
- 逐项入口由客服先选分类，不需要自动猜分类。
- 文字是字段识别和对齐的主要来源。每个候选必须带原消息标识、发送人、消息时间和证据片段；同一字段有多个值时全部保留供客服选择。
- 图片分类本身不等于正式案件材料生效。客服确认映射后，仍须遵守现有 `case_file` 分类、版本、角色和案件状态约束。

## 实施约束

- 保持 Java 21、Spring Boot 4.1.1、Vue 3、Element Plus、PostgreSQL、MyBatis-Plus/MyBatis XML、Flyway、MinIO `ObjectStorageService` 和 PostgreSQL 任务 Worker；不引入微服务或 RabbitMQ。
- 建议新增独立业务领域，避免把整包解析和候选审核塞入现有 `document`、`ocr` 或 `workorder` Controller。具体包名和表结构在未决问题关闭后确定。
- 文件夹上传是浏览器多文件选择，必须保留相对路径；ZIP 在服务端有界解压。两种输入归一成同一内部消息/附件模型，但不要为了“统一”丢失原始包及原相对路径。
- 服务端执行角色、数据范围、字段可见性、状态门禁和审计。日志、异常及审计摘要不得输出聊天正文、完整手机号、车牌或对象键。
- 测试必须使用合成脱敏聊天文本和图片占位文件，覆盖路径穿越、压缩炸弹、重复导入、丢失附件、同名附件、冲突字段、上下文不足、越权和并发确认。
