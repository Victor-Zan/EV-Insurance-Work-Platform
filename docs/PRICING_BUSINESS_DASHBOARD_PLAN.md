**3. 核损变化后的本版金额规则**

原平台的百分比加价以网点报价为基数。按照本次“加价比率不变”的要求，本计划按同一基数定义推导核损后的网点金额。

| 符号 | 含义 |
| --- | --- |
| B₀ | 原正式报价对应的加价前总额，保存该版本实际使用的基数 |
| r | 原有效百分比加价率，例如 20% 按 0.20 计算 |
| T₀ | 原对外报价，T₀ = B₀ × (1 + r) |
| A | 当前有效且经确认的核损金额，本计划用作本版拆分总额 |
| S | 核损后网点确认价格，S = A ÷ (1 + r) |
| P | 本版加价盈利，P = A − S |

示例采用可整除金额，便于确认业务含义。

| 项目 | 核损调整前 | 核损下调后 |
| --- | --- | --- |
| 原网点报价 B₀ | 1,000.00 元 | 历史原报价仍为 1,000.00 元 |
| 加价率 r | 20% | 20% |
| 对外报价／当前核损金额 | 1,200.00 元 | 1,080.00 元 |
| 网点确认价格 S | 1,000.00 元 | 900.00 元 |
| 加价盈利 P | 200.00 元 | 180.00 元 |

本版保险应收拟采用 A，网点应付采用 S，平台加价盈利采用 P。实际到账、实际结算继续记录真实发生金额并关联各自目标。原始报价明细、原报价总额及原加价额保留，核损调整产生独立确认结果，金额调整发生在总额层面。

现有 `confirmedAmount` 允许独立于核损金额，且被前端同时用于应收和应付，这与本版拆分要求存在直接差异。本计划建议新规则工单在原核损确认页确认 A、S、P 三个结果，历史独立确认价保留在历史依据中。该页面调整与新旧规则启用边界需在实施阶段 A 签收。

金额确认应在后端同一事务内计算、校验并保存。记录正式报价版本、核损版本、确认人、确认时间、规则版本、原始基数、原加价方式与值、最终拆分金额。前端预览提交时，服务端再次核验依据版本。读取页面只读取结果。

以下边界在阶段 A 确认后进入金额实现。

| 边界 | 当前事实与建议 |
| --- | --- |
| 固定金额加价 | 原平台同时支持固定金额。建议由原加价额 M₀ 与 B₀ 形成等效比率，按 S = A × B₀ ÷ (B₀ + M₀) 精确计算，避免提前把比率舍入；该扩展尚待确认 |
| 分币舍入 | 原平台比例加价采用 HALF_UP 到分。新除法建议先对 S 按该方式取两位，再用 A − S 得到 P，使分币合计一致；新除法舍入规则尚待确认 |
| 零值 | 百分比为零时 S = A、P = 0。A 为零时拆分均为零。B₀ 为零的固定金额工单等效比例无定义，需单独确认兼容处理 |
| 核损上调 | 同一公式会使 S 对应上升；用户已明确下调逻辑，上调是否同样适用需在规则验收时确认 |
| 已开修或已完成后改价 | 核查并沿用现有修订状态门禁；若业务需要开放修订，应另行确认允许节点和重确认方式 |

规则版本使用明确标识，例如 `ASSESSMENT_KEEP_MARKUP_RATE_V1`。未来修改规则时新增版本，历史案件继续关联其已确认版本。

**5. 指标口径与数据权限**

当前新流程中，`COMPLETED` 表示回款和网点结算均已确认完成。本计划沿用此正式完成节点，维修完工与车主收车时间分别留作流程记录。利润时间取有效完成事件时间，避免使用随其他编辑变化的 `updated_at`。

| 指标 | 口径 |
| --- | --- |
| 已完成工单数 | 当前具有有效完成资格、满足时间和归属筛选的工单数，每单一次 |
| 有效核算工单数 | 已完成且具有完整可追溯金额快照的工单数 |
| 待核算工单数 | 已完成工单数减有效核算工单数，可查看缺失依据 |
| 核损金额／网点确认金额合计 | 分别汇总同一有效核算集合的 A 与 S |
| 加价盈利合计 | 同一集合的 ΣP，并满足 ΣA − ΣS = ΣP |
| 平均单案盈利 | ΣP ÷ 有效核算工单数 |
| 整体加价率 | ΣP ÷ ΣS；S 为核损后对应的加价基数，分母为零时显示“—” |
| 原报价基数合计 | 展示原 B₀ 的历史口径，列名与核损后 S 明确区分 |

金额统计覆盖已完成工单，资金收支页面可查询其他阶段的案件。点击趋势图同时传递时间桶、对象与权限范围。所有汇总、趋势、排名、分页明细使用同一过滤口径。

| 角色 | 经营看板与明细 | 配件价格库 |
| --- | --- | --- |
| ADMIN | 平台整体、全部网点与客服，查看单案核算依据 | 沿用原管理权限 |
| CUSTOMER_SERVICE | 仅创建者为当前用户的工单；网点筛选在本人范围内生效 | 沿用原日常价格运营权限 |
| REPAIR_SHOP | 在本店本派单结算摘要中查看确认应付与累计结算 | 沿用角色访问限制 |
| OWNER | 沿用原案件进度和收车信息范围 | 沿用角色访问限制 |

新看板的后端查询强制附加创建者条件，客服不能通过传入其他客服 ID 扩大范围。筛选候选名称、汇总数量和明细接口同步过滤。客服的既有办单协作权限是另一条授权链路，新增经营权限应在专用接口实现，并单独验收两条链路。管理员自己创建的工单计入平台与网点结果，客服归属栏显示“管理员创建”，保证总数可对账。

**6. 工单需要同步的经营数据**

| 时点 | 数据 | 使用方式 |
| --- | --- | --- |
| 正式建单 | 工单 ID、编号、创建者 ID、车辆品牌车型 | 确定业绩归属；保留创建者标识，即使姓名变更仍可追溯 |
| 派单／改派 | 实际承修网点 ID、派单版本及生效状态 | 完成时取最终有效承修关系；展示网点使用真实组织标识 |
| 网点报价／正式报价 | 原始报价版本、正式报价版本、B₀、加价方式和值、原加价额 | 提供比例规则依据；配件行可另行进入价格核对列表 |
| 核损最终确认 | A、S、P、报价与核损版本、确认人、规则版本 | 形成有效的金额确认快照，服务端提供资金目标来源 |
| 回款／结算 | 各方向目标版本、分笔净金额、确认状态 | 供资金页面对账，并驱动原完成门禁 |
| 正式完成 | 完成事件与时间、创建者、最终网点、有效金额快照引用 | 在完成事务内建立经营快照并获得统计资格 |
| 冲销／确认失效／退出完成 | 失效原因、对应状态事件与历史快照引用 | 使原快照退出有效统计集合，历史依据可查 |

建议在现有应用服务事务内建立快照，统计接口从已保存事实聚合。关联报价、资金和审计记录在同一业务事务中保持一致。重复完成请求与并发确认依靠工单版本、幂等键和完成事件唯一约束避免重复计入。

原资金代码支持完成后冲销并回退阶段。计划采用“当前有效完成集合”口径，回退后从原完成时间桶撤出，重新完成后按新完成事件计入一次，并保留两次事件历史。该方案意味着旧月份查询可能因有效状态变化而更新，需在阶段 A 签收。经营快照保留不可变历史，通过单独有效状态或关联事件控制当前统计资格。

**7. 配件价格库的数据与页面**

沿用现有品牌、车型、标准配件和适配关系。用户界面以标准配件及其参考价格为中心，来源明细支持多家、多次询价。

| 数据层 | 每条记录的字段 | 必填与处理 |
| --- | --- | --- |
| 标准配件 | 内部标识、标准名称、计量单位 | 名称和单位必填，内部标识由现有规则管理 |
| 车型适配 | 车辆品牌、车型、配件关联 | 一个配件可以适配多个车型，匹配完成后用于参考查询 |
| 辅助编码 | OE码、厂家编码 | 有资料时填写，冲突或多解交给人工核对 |
| 价格样本 | 对应配件、金额、单位、配件品牌、地区、导入日期 | 金额和单位明确后进入参考集合，导入日期由系统记录；品牌／地区缺失保留“未注明”分组 |
| 来源依据 | 小帮帮／市场询价／网点报价、来源文件或案件、原始行号或行标识、原始名称、原始金额 | 原始上下文可追溯，来源与文件格式分别记录 |
| 核对记录 | 匹配结果、异常原因、核对状态、核对人、时间、有效版本 | 待核对样本与已确认样本有明确状态 |

原始资料为总价时，采集数量、单位和“单价／总价”语义，用于核对单价。原金额始终保留，新增单价换算舍入须单独确认。价格库沿用已有 CNY、正数及两位小数输入校验，旧数据单位缺失时先补齐依据。

“车辆品牌”来自车型目录，“配件品牌”来自样本，两者分列。不同计量单位以及不同价格业务性质分别聚合。原平台四类参考价格属于不同业务性质，迁入新视图时保留原分类，避免将平台对外价与网点进货或报价混为同一价格区间。

| 页面 | 改造内容 |
| --- | --- |
| 参考查询 | 品牌→车型→配件联动，地区、来源与导入日期筛选，使用名称搜索和分页候选 |
| 参考结果 | 按可比条件分组，展示记录数量、最低价、最高价、最近导入日期，以及来源明细 |
| 配件资料 | 标准名称、计量单位、适配车型和可选编码，在现有目录页面完善 |
| 数据导入 | 上传原始资料、字段映射、预览、核对、确认，支持追溯导入批次 |
| 待核对列表 | 展示异常原因和原始行，对应匹配、补充、修正或排除动作 |
| 报价审核中的参考入口 | 在现有报价审核行旁打开参考面板，带入已确认车型；名称多解时由客服选择标准配件 |

参考统计使用全部符合条件且已确认的样本，分页只作用于明细。导入日期按首次采集时间的中国自然日计算。更正一个样本时追加修订并只统计当前有效修订，沿用首次导入日期。独立来源的多次真实报价分别保留。无可比记录时显示零条及空结果。

原价格版本的“生效日期”用于版本管理。新样本查询使用“导入日期”，价格范围标明计量单位。

**8. 采集、清洗与旧价格模型兼容**

建议按“采集原始样本 → 匹配配件与车型 → 标记异常 → 人工核对 → 确认参考样本 → 查询引用”的路径处理。

车型未匹配、单位缺失和金额格式错误可以根据确定规则自动标记。价格明显异常先由人工标记；若后续需要数值阈值，应依据真实样本另行确认阈值和例外处理。

原模型 `price_record` 的唯一维度为配件、车型、价格类型和组织范围，`price_version` 要求同维度有效期互斥。会议要求同日多来源报价可并列，因此直接把所有样本追加为旧价格版本会发生冲突。

计划在现有 `pricing` 领域增加独立的价格样本与核对记录，复用原主数据、来源目录、解析器、审计和权限。旧参考价格版本继续承载其已确认历史；新参考查询将明确来源标识与业务性质。具体表名在数据库设计阶段确定。

| 场景 | 处理方案 |
| --- | --- |
| 小帮帮导出 | 先用真实脱敏样表验证字段映射，保存文件指纹、来源行和原值，再进行标准配件匹配 |
| 市场询价 | 手工录入或模板采集，保留询价日期、地区、来源说明和配件条件 |
| 网点报价 | 由客服明确采集已提交报价中的配件行，绑定报价版本和行号，进入相同核对流程 |
| 同一文件重复上传 | 文件指纹与来源行识别重复；来源系统有稳定记录 ID 时优先使用该 ID |
| 不同来源同金额 | 保留为不同样本；疑似重复由人工核对，去重依据包含来源身份 |
| 非配件或费用混合行 | 排除工时行；配件与工时混价的行待核实配件价格后使用 |
| 旧参考价格 | 保留原版本及业务分类，补足单位后建立可追溯映射；统计避免原记录与映射样本双计 |

现有结构化导入的整批原子提交继续作为独立兼容入口。新增采集先保存待核对样本，用户选定并明确确认的合格集合在事务内提交，剩余条目留在待核对状态，批次分别显示已采集、已确认、待核对和已排除数量。

原价格导入仅保留摘要与字段，原文件需要长期追溯时，通过统一 `ObjectStorageService` 保存私有来源文件并绑定批次权限。引用已有网点报价原件时继续执行材料访问规则。批量解析、主数据匹配和确认采用分批与数据库批量查询，所有列表稳定分页并限制单页上限。

**9. 后端、接口与历史数据改造**

工程沿用现有模块化单体、Java／Spring Boot、PostgreSQL、MyBatis 和 Flyway。业务调整集中在 `pricing`、`quotation`、`funds`，工单领域提供完成与失效事件的事务协作入口。

| 改动 | 拟采用的方式 |
| --- | --- |
| 核损金额拆分 | 在 `quotation` 增加本版金额计算和确认快照，现有确认入口内复用版本、权限、幂等及审计 |
| 资金目标 | `funds` 从服务端有效确认快照取得各方向金额；旧人工目标入口按工单规则版本校验，避免绕过本版拆分 |
| 经营快照 | 保存完成事件、创建者、最终网点、原报价依据、A／S／P 和规则版本，关联不可变审计 |
| 看板接口 | 在 `/api/v1/funds/analytics` 下规划 summary、trend、shops、creators、cases，接口名在 API 设计时定稿 |
| 价格参考接口 | 在原 `/api/v1/pricing` 下扩展样本采集、核对、参考汇总与分页明细，旧价格接口保留清晰契约 |
| 查询性能 | 围绕完成时间与创建者／网点建立索引，数据库聚合共用过滤条件，记录执行计划；价格数据按十万级规模验证 |
| 图表数据 | 后端返回精确金额字符串及明确单位，展示层转换仅用于绘制坐标，标签与明细采用原精确值 |

所有数据库变更采用新增迁移，正式编号在实施时根据当前迁移序列分配。需要补充的对象包括配件单位与辅助编码、来源样本和核对历史、核损拆分快照、完成经营快照及索引。

历史工单按证据分类迁移。可以取得真实完成事件、创建者、最终网点和明确金额依据的案件，使用对应历史规则建立快照；缺失依据的案件列为待核算，保留原因。用户最新规则从明确启用点开始应用，旧已完成工单的追溯转换需单独确认。独立历史档案的字段与正式工单不同，首版先在原档案入口查询，其纳入经营统计的转换另行评审。

新规则启用时还需区分已开修、已有回款／付款和未确认报价的在途案件。建议先对新确认案件启用，存量案件经过兼容检查后逐批处理。若新网点目标低于已有净付款，应进入既有冲销或人工处理流程，避免产生与真实流水冲突的目标。

**10. 实施阶段与每阶段交付**

| 阶段 | 工作内容 | 验收与下一阶段入口 |
| --- | --- | --- |
| A 规则与样表签收 | 确认比例公式、固定金额处理、分币舍入、独立最终确认价交互、历史规则边界；用脱敏样表确定价格字段映射 | 形成金额案例表、样表映射、页面流程及未决项处理结论，相关实现条件齐备 |
| B 配件参考数据 | 配件字段补齐、样本采集、待核对列表、来源追溯、参考统计；接入原报价审核参考入口 | 三类来源可采集；异常可处理；统计和明细一致；重复导入可追溯；旧模板与版本查询回归通过 |
| C 核损与结算金额 | 比例保持规则、核损确认交互、应收应付拆分、网点金额展示、完成快照及失效处理 | 金额示例、舍入、并发、权限、冲销和历史兼容测试通过，单案收支可核对 |

| E 联调验收 | 价格参考→报价→核损→维修→收车→回款→结算→经营看板的端到端验证及数据兼容演练 | 真实流程验收、迁移验证、性能记录、回归结果、上线清单齐备 |

每阶段更新 `docs/PROGRESS.md`，提供结果后按仓库阶段门禁停止，由用户确认进入下一阶段。实施耗时在阶段 A 完成样表核查后估算。
