## D-026：案件材料、对象存储与后续全字段 OCR（2026-10-07，已由 D-027 取代）

- 决策：材料内容只经 `ObjectStorageService` 保存到 MinIO，数据库保存受控对象键和元数据；对象键和 SHA-256 不返回客户端。允许 PDF/JPG/JPEG/PNG，单文件 10 MiB、每分类 20 个，保险通知书正式提交前必传，到店照片到店确认前必传，其他阶段 4 材料可选；不提供自动删除。OCR 本阶段不执行，后续必须覆盖材料中所有可识别信息并经人工确认后写正式字段。
- 理由：满足材料留存、权限和后续供应商替换，同时避免未经核对的 OCR 直接污染案件数据。
- 代价：数据库与对象存储不是同一事务，只能在元数据失败时补偿删除；真实 OCR 的准确率、成本、字段映射和重试留到下一阶段验证。

本文件记录影响多个模块或后续维护成本的重要决策。状态使用：`已接受`、`待确认`、`已取代`。已接受决策如需改变，应新增决策说明原因，不应静默改写历史。业务细节未确认时只记录约束，不代替产品决定。

## D-001：采用模块化单体

- 状态：已接受
- 决策：后端为一个可部署的 Spring Boot 应用，按业务领域划分模块，不使用微服务。
- 理由：MVP 的核心难点是跨报价、核损、授权、维修和结算记录的一致流程，单体事务和本地调试更直接。
- 优势：部署简单、事务边界清楚、联调成本低、早期迭代快。
- 代价：模块不能独立扩缩；若缺少边界约束容易退化为大泥球。
- 约束：坚持 package-by-feature，跨模块通过明确应用接口协作，不建立全局巨型 Controller/Service/Mapper 目录。

## D-002：管理端与移动 H5 分为两个 Vue 应用

- 状态：已接受
- 决策：管理端使用 Element Plus，网点/车主 H5 使用 Vant，分别构建。
- 理由：桌面后台与移动触控的组件和交互差异明显，分应用比在一个包中同时维护两套组件库更清晰。
- 优势：包体和路由边界清楚，可分别发布；避免 CSS 和组件依赖互相污染。
- 代价：认证客户端、API 类型和少量工具可能重复。
- 约束：不在初始化时创建复杂共享组件库；只有出现稳定重复后再提取。

## D-003：后端使用 Java 21、Spring Boot 3.5

- 状态：已接受
- 决策：Java 21 作为编译与运行基线，Spring Boot 3.5 提供 Web、事务、安全、校验和可观测性基础。
- 理由：LTS Java 与成熟企业生态适合包含金额、权限、审计和长期维护的系统。
- 优势：强类型、库生态成熟、事务和安全集成完善。
- 代价：资源占用和框架复杂度高于部分轻量技术栈。
- 本地验证：主机仅安装 Java 24.0.2；阶段 1 已使用 Eclipse Temurin Java 21.0.12.1 容器完成 `clean verify` 和实际启动验证。日常宿主机开发仍建议安装 Java 21 并配置 `JAVA_HOME`。

## D-004：PostgreSQL 作为统一业务数据库

- 状态：已接受
- 决策：业务、价格库、审计索引和 MVP 异步任务使用 PostgreSQL。
- 理由：事务、约束、索引、批量能力和精确数值类型与本项目高度匹配。
- 优势：减少早期基础设施数量；便于保证状态、金额和审计的一致性；支持复杂价格检索。
- 代价：在线业务、批量导入和 Worker 会竞争同一数据库资源。
- 约束：使用索引、分页、批处理、连接池和慢查询/执行计划验证；性能数据不足时不提前分库。

## D-007：Spring Security + JWT + RBAC，并叠加数据范围校验

- 状态：已接受（登录与 Token 生命周期已由 D-018 细化）
- 决策：Spring Security 负责认证链，JWT 适配前后端分离，RBAC 表达功能权限；网点归属、车主本人范围和敏感字段由服务端额外校验。
- 理由：仅 RBAC 无法表达“同角色只能看自己的案件”，仅前端隐藏也不能提供安全性。
- 优势：职责分层，可自动化测试越权场景。
- 代价：JWT 撤销、续签、权限变更生效策略需额外设计。

## D-008：金额与报价分层保存

- 状态：已接受（精度和舍入细节待确认）
- 决策：Java 金额用 `BigDecimal`，数据库用显式 `DECIMAL/NUMERIC`；原始报价、加价、正式报价、核损、回款和网点结算分别表达，不反复覆盖同一金额字段。
- 理由：不同金额的责任方、可见范围和审计意义不同。
- 优势：历史可追溯，权限过滤明确，避免浮点误差。
- 代价：数据模型和 DTO 数量增加；需要明确舍入与精度规则。

## D-009：价格采用不可变版本

- 状态：已接受
- 决策：价格更新新增版本，通过生效/失效时间、来源和导入批次追踪；历史案件保留当时快照或稳定版本引用。
- 理由：需求明确禁止覆盖历史，核损与结算需要可追溯。
- 优势：可以复盘任意时点价格，支持审计和数据质量追责。
- 代价：查询需判断有效期，数据量增长更快，冲突处理更复杂。
- 约束：不使用“更新金额字段”代替版本新增；唯一键和版本冲突策略在价格库阶段确认。

## D-010：文件使用 MinIO，并通过统一接口访问

- 状态：已接受
- 决策：附件内容存 MinIO，业务只依赖 `ObjectStorageService`；PostgreSQL 存文件元数据和关联。
- 理由：避免大文件进入关系库，并为未来替换云对象存储留出边界。
- 优势：本地可复现、S3 生态兼容、业务与供应商解耦。
- 代价：数据库与对象存储无法使用同一事务，需处理孤儿对象和失败补偿。

## D-012：异步任务使用 PostgreSQL 任务表

- 状态：已接受
- 决策：MVP 不引入 RabbitMQ，定时 Worker 从 PostgreSQL 任务表安全领取并执行任务。
- 理由：当前异步规模有限，减少一个中间件和分布式一致性问题。
- 优势：部署简单，可与业务事务协调，任务状态易查询。
- 代价：轮询负载、吞吐和路由能力有限。
- 约束：任务处理幂等、领取并发安全、有界重试、失败可观测；只有指标证明需要时才评估消息队列。
