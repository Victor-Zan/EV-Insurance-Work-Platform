## D-021：价格自然日版本与受控截止（2026-10-04，已接受）

用户本次确认取代此前对有效期完全不可修改的描述：金额必须大于零，CNY NUMERIC(18,2)，拒绝额外小数位。有效期为中国自然日 DATE，首尾包含；无期限旧版本允许在新增版本的同一事务内补齐截止日为新开始日前一天。新开始日严格晚于最新版本开始日；已有有限区间不能覆盖或缩短。金额、来源及创建信息不可覆盖或删除，自动截止必须审计，并保留 previous_version_id / closed_by_version_id 关联。数据库同时拒绝有效期重叠和任意历史字段修改，手工及导入复用同一规则。

正式价格适用优先级仍待确认，候选查询不选择最终价、不自动回退或加价。

## D-022：价格导入预览与整批原子确认（2026-10-04，已接受）

- XLSX / UTF-8 CSV 使用有界流式解析，单文件 10 MiB / 20,000 行；不保存上传文件或接入对象存储。保存文件摘要、30 分钟预览、批次与错误上下文，使确认对象可追溯。
- 预览只写暂存；管理员显式确认后复用手工版本规则及批量应用 SQL，重新校验主数据、文件内重复与数据库最新版本。按价格维度排序获取事务锁，避免并发覆盖。
- 任意行错误使整批正式价格零写入。数据库冲突回滚全部价格、截止日和对应审计后，在独立事务记录失败批次；确认幂等，重复请求返回原批次。不会把失败记录伪装成部分成功。
- 金额、自然日、同维度版本与有效期不重叠由 API、导入和 PostgreSQL 约束共同保护。来源字典与版本快照独立于 CSV/Excel 上传格式；基础资料必须预先维护，不在导入时推测创建。
- 代价：暂存与错误数据占用数据库空间，单次文件有明确上限；十万级验证使用独立非生产批量夹具，不放宽导入上限，不作生产性能承诺。
- 正式价格适用优先级仍待业务确认，当前候选并列返回。共享分支 feature/sherr-price-database 普通提交与推送，Draft PR 指向 main，不重写共享历史或自行合并。

## D-024：案件 UUID、正式编号与车主绑定（2026-10-07，已接受）

- 决策：案件内部标识使用 UUID；正式提交时按中国业务日期生成 `EVR-YYYYMMDD-######`，草稿无展示编号。保险公司 + 报案号对正式案件唯一；手机号/车辆命中在办案件只警告并要求显式确认。正式提交按完整手机号精确匹配唯一已启用 OWNER，未唯一命中保持待匹配，不自动开户。
- 理由：分离技术标识与业务展示号，避免草稿占号；同时防止重复理赔案件和不安全的默认账号。
- 代价：展示编号需要数据库日计数器；手机号变化或重复账号需要后续人工绑定流程。

## D-025：阶段 4 使用显式指派版本与到店前状态机（2026-10-07，已由 D-027 取代）

- 决策：状态只允许 `DRAFT → PENDING_DISPATCH → PENDING_ACCEPTANCE → PENDING_ARRIVAL → ARRIVED` 及已确认的拒单、取消、到店前改派分支。每次派单新增 assignment_version；状态操作使用幂等键、乐观版本、事务历史和审计。未到店异常不改变状态，只写原因并设置待跟进标记；到店照片至少一张，到店后禁止普通改派。
- 理由：拒绝可被任意状态更新或覆盖旧派单记录，使客服、网点和审计看到同一条可复盘时间线。
- 代价：后续报价/维修状态必须新增明确转换，不能复用通用回滚接口。

## D-026：案件材料、对象存储与后续全字段 OCR（2026-10-07，已由 D-027 取代）

- 决策：材料内容只经 `ObjectStorageService` 保存到 MinIO，数据库保存受控对象键和元数据；对象键和 SHA-256 不返回客户端。允许 PDF/JPG/JPEG/PNG，单文件 10 MiB、每分类 20 个，保险通知书正式提交前必传，到店照片到店确认前必传，其他阶段 4 材料可选；不提供自动删除。OCR 本阶段不执行，后续必须覆盖材料中所有可识别信息并经人工确认后写正式字段。
- 理由：满足材料留存、权限和后续供应商替换，同时避免未经核对的 OCR 直接污染案件数据。
- 代价：数据库与对象存储不是同一事务，只能在元数据失败时补偿删除；真实 OCR 的准确率、成本、字段映射和重试留到下一阶段验证。

## D-027：按权威分步提示词纠正阶段 4 边界与状态机（2026-10-08，已接受）

- 决策：阶段 4 只实现工单核心、派单及到店前异常流程。文件、MinIO、`ObjectStorageService`、Mock OCR 和 Mock 地图全部归入提示词 5，不作为正式建单或确认到店门槛。案件通知单可在草稿或正式建单后上传，但只在进入报价审核前要求“已上传或填写缺失原因”。
- 正式建单门槛以权威提示词为准：保险公司、报案号、事故时间/简述/区域、车主姓名/手机号、车辆品牌/车型，以及 VIN、牌照、其他认可编号至少一个；报案时间、保单号和详细地址可空。数据来源、当前负责人等由系统填写。
- `ARRIVAL_EXCEPTION` 是独立状态，可继续等待、取消派单、改派或取消整个工单。已接单未到店改派要确认车辆未到店；已到店仅管理员可异常改派并填写原因和转运说明。取消整个正式工单保留全部历史，不提供通用回退。
- 强重复严格使用保险公司 + 报案号并由数据库唯一约束兜底；四类疑似重复按管理员可配置的默认 7 天窗口判断，继续操作必须记录原因。幂等命令保存并返回第一次响应；同网点、同派单版本重复接单/到店语义成功但不重复落日志。
- 理由：D-025/D-026 混入了提示词 5 的材料能力，并把到店异常降为提醒标记，与权威需求不一致。本决策显式取代其冲突部分，同时保留 UUID、业务编号、车主绑定、指派版本、审计和 Provider 抽象的长期方向。
- 代价：阶段 4 暂时不能上传附件或使用地图；进入提示词 5 时必须新增迁移和接口，不得回改已经用于共享环境的 V5。

## 使用方式

本文件记录影响多个模块或后续维护成本的重要决策。状态使用：`已接受`、`待确认`、`已取代`。已接受决策如需改变，应新增决策说明原因，不应静默改写历史。业务细节未确认时只记录约束，不代替产品决定。

## D-001：采用模块化单体

- 状态：已接受
- 决策：后端为一个可部署的 Spring Boot 应用，按业务领域划分模块，不使用微服务。
- 理由：MVP 的核心难点是跨报价、核损、授权、维修和结算记录的一致流程，单体事务和本地调试更直接。
- 优势：部署简单、事务边界清楚、联调成本低、早期迭代快。
- 代价：模块不能独立扩缩；若缺少边界约束容易退化为大泥球。
- 约束：坚持 package-by-feature，跨模块通过明确应用接口协作，不建立全局巨型 Controller/Service/Mapper 目录。

## D-002：管理端与移动 H5 分为两个 Vue 应用

- 状态：已接受
- 决策：管理端使用 Element Plus，网点/车主 H5 使用 Vant，分别构建。
- 理由：桌面后台与移动触控的组件和交互差异明显，分应用比在一个包中同时维护两套组件库更清晰。
- 优势：包体和路由边界清楚，可分别发布；避免 CSS 和组件依赖互相污染。
- 代价：认证客户端、API 类型和少量工具可能重复。
- 约束：不在初始化时创建复杂共享组件库；只有出现稳定重复后再提取。

## D-003：后端使用 Java 21、Spring Boot 3.5

- 状态：已接受
- 决策：Java 21 作为编译与运行基线，Spring Boot 3.5 提供 Web、事务、安全、校验和可观测性基础。
- 理由：LTS Java 与成熟企业生态适合包含金额、权限、审计和长期维护的系统。
- 优势：强类型、库生态成熟、事务和安全集成完善。
- 代价：资源占用和框架复杂度高于部分轻量技术栈。
- 本地验证：主机仅安装 Java 24.0.2；阶段 1 已使用 Eclipse Temurin Java 21.0.12.1 容器完成 `clean verify` 和实际启动验证。日常宿主机开发仍建议安装 Java 21 并配置 `JAVA_HOME`。

## D-004：PostgreSQL 作为统一业务数据库

- 状态：已接受
- 决策：业务、价格库、审计索引和 MVP 异步任务使用 PostgreSQL。
- 理由：事务、约束、索引、批量能力和精确数值类型与本项目高度匹配。
- 优势：减少早期基础设施数量；便于保证状态、金额和审计的一致性；支持复杂价格检索。
- 代价：在线业务、批量导入和 Worker 会竞争同一数据库资源。
- 约束：使用索引、分页、批处理、连接池和慢查询/执行计划验证；性能数据不足时不提前分库。

## D-005：MyBatis-Plus 与 MyBatis XML 分工使用

- 状态：已接受
- 决策：简单单表 CRUD/分页优先 MyBatis-Plus；复杂查询、批量和性能敏感 SQL 使用 XML。
- 理由：在减少样板代码的同时保留 SQL 可控性，尤其适合十万级价格库。
- 优势：开发效率与查询可调优性兼顾。
- 代价：团队需维护明确边界，XML 与 Java 模型可能漂移。
- 约束：不为证明使用某技术而强行混用；复杂 SQL 必须有数据库集成测试。

## D-006：Flyway 是唯一数据库结构演进机制

- 状态：已接受
- 决策：禁止依赖 Hibernate 自动建表，所有结构与受控基础数据变化使用 Flyway。
- 理由：确保本地、测试和未来生产环境可重复、可审查。
- 优势：变更历史明确，可在 CI/部署前验证。
- 代价：迁移编写与冲突处理需要纪律。
- 约束：共享环境执行过的迁移只追加不修改。

## D-007：Spring Security + JWT + RBAC，并叠加数据范围校验

- 状态：已接受（登录与 Token 生命周期已由 D-018 细化）
- 决策：Spring Security 负责认证链，JWT 适配前后端分离，RBAC 表达功能权限；网点归属、车主本人范围和敏感字段由服务端额外校验。
- 理由：仅 RBAC 无法表达“同角色只能看自己的案件”，仅前端隐藏也不能提供安全性。
- 优势：职责分层，可自动化测试越权场景。
- 代价：JWT 撤销、续签、权限变更生效策略需额外设计。

## D-008：金额与报价分层保存

- 状态：已接受（精度和舍入细节待确认）
- 决策：Java 金额用 `BigDecimal`，数据库用显式 `DECIMAL/NUMERIC`；原始报价、加价、正式报价、核损、回款和网点结算分别表达，不反复覆盖同一金额字段。
- 理由：不同金额的责任方、可见范围和审计意义不同。
- 优势：历史可追溯，权限过滤明确，避免浮点误差。
- 代价：数据模型和 DTO 数量增加；需要明确舍入与精度规则。

## D-009：价格采用不可变版本

- 状态：已接受
- 决策：价格更新新增版本，通过生效/失效时间、来源和导入批次追踪；历史案件保留当时快照或稳定版本引用。
- 理由：需求明确禁止覆盖历史，核损与结算需要可追溯。
- 优势：可以复盘任意时点价格，支持审计和数据质量追责。
- 代价：查询需判断有效期，数据量增长更快，冲突处理更复杂。
- 约束：不使用“更新金额字段”代替版本新增；唯一键和版本冲突策略在价格库阶段确认。

## D-010：文件使用 MinIO，并通过统一接口访问

- 状态：已接受
- 决策：附件内容存 MinIO，业务只依赖 `ObjectStorageService`；PostgreSQL 存文件元数据和关联。
- 理由：避免大文件进入关系库，并为未来替换云对象存储留出边界。
- 优势：本地可复现、S3 生态兼容、业务与供应商解耦。
- 代价：数据库与对象存储无法使用同一事务，需处理孤儿对象和失败补偿。

## D-011：OCR、地图和短信采用端口 + Mock

- 状态：已接受
- 决策：定义 `OcrProvider`、`MapProvider` 和短信端口；MVP 使用明确标识的 Mock，站内通知是真实 MVP 功能。
- 理由：供应商尚未选择，但业务流程和测试不能被外部采购阻塞。
- 优势：可替换、可测试、无供应商锁定。
- 代价：Mock 不代表真实服务的准确率、延迟、限流和错误特征。
- 约束：Mock 不得在生产配置中伪装成真实成功；真实接入另设验收。

## D-012：异步任务使用 PostgreSQL 任务表

- 状态：已接受
- 决策：MVP 不引入 RabbitMQ，定时 Worker 从 PostgreSQL 任务表安全领取并执行任务。
- 理由：当前异步规模有限，减少一个中间件和分布式一致性问题。
- 优势：部署简单，可与业务事务协调，任务状态易查询。
- 代价：轮询负载、吞吐和路由能力有限。
- 约束：任务处理幂等、领取并发安全、有界重试、失败可观测；只有指标证明需要时才评估消息队列。

## D-013：REST + OpenAPI + 统一响应和异常

- 状态：已接受
- 决策：前后端通过版本化 REST API 协作，OpenAPI 作为可验证契约；统一响应包含 `code`、`message`、`data`、`traceId`；列表统一分页。
- 理由：适合两个浏览器客户端，便于联调、测试与生成类型。
- 优势：边界清晰、工具成熟、错误行为一致。
- 代价：需要持续防止文档与实现漂移。

## D-014：Docker Compose 用于本地，不等同生产方案

- 状态：已接受
- 决策：本地依赖通过 Docker Compose 启动，敏感值来自环境变量并提供 `.env.example`；未来云端部署保持镜像和配置可迁移。
- 理由：降低开发环境差异，同时不提前绑定某家云厂商。
- 优势：依赖版本可复现、上手路径明确。
- 代价：Compose 不提供生产所需的高可用、密钥、备份和弹性能力。

## D-015：MVP 只记录资金状态，不处理真实资金

- 状态：已接受
- 决策：记录保险公司回款与维修网点结算信息；不接支付通道，不自动分账，最终网点结算金额可空且人工录入。
- 理由：与明确业务范围一致，避免把支付合规和资金安全风险带入第一版。
- 优势：显著降低范围、合规和技术复杂度。
- 代价：需依赖线下操作和人工对账，系统记录可能滞后。

## D-016：自动收车、货拉拉和真实供应商集成不进入 MVP

- 状态：已接受
- 决策：自动确认收车只保留未来扩展能力，不设置定时任务；货拉拉不接；OCR、地图、短信不选择真实供应商。
- 理由：严格控制 MVP 范围，避免未经确认的外部依赖。
- 代价：部分流程仍依赖人工，Mock 不能用于评价真实集成质量。

## D-017：本地 MinIO 使用固定的社区版兼容镜像

- 状态：已接受（仅限本地开发）
- 决策：Compose 使用 `bitnamilegacy/minio:2025.7.23-debian-12-r5`，数据挂载到 `/bitnami/minio/data`；业务仍只依赖 MinIO/S3 行为和未来的 `ObjectStorageService`，不依赖 Bitnami 脚本。
- 理由：原 `minio/minio` Docker Hub 仓库已归档且当前环境拒绝匿名拉取；该固定镜像仍可公开获取并已通过健康检查，足以作为本地对象存储。
- 优势：本地可启动、版本固定、不引入商业服务或真实云账号。
- 代价：Legacy 镜像不再持续更新，不得作为未来生产镜像；进入部署加固阶段前必须重新评估受维护的 MinIO/兼容对象存储发行方式。

## D-018：数据库账号、BCrypt 与 JWT 重新登录

- 状态：已接受（细化 D-007，2026-10-03）
- 使用账号/密码，数据库存启用状态、角色与 BCrypt 哈希。JWT 仅携带用户标识、签发/过期时间和认证版本，密钥及有效期从环境变量读取，示例有效期 30 分钟。
- 第一版不提供刷新 Token；过期重新登录。每次请求查询实时启用状态和权限；停用、密码重置、角色与网点归属修改递增认证版本，旧 Token 失效。
- 开发测试账号通过显式 dev 配置和环境变量注入的密码初始化，禁止明文进入仓库或日志。重置接口只返回成功状态。
- 代价：每次认证访问数据库；换取停用和权限变化立即生效。

## D-019：区域树与网点服务区域多对多

- 状态：已接受（2026-10-03）
- 区域支持省、市、区县及父子约束；网点服务区域为独立多对多表。网点账号关联表以 user_id 唯一约束保证一个账号一个网点，同时允许一个网点多个账号。
