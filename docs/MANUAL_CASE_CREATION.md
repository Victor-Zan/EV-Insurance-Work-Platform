# 纯手工建单核查与恢复验证（2026-10-22）

## 结论与范围

在远程 main `f3e3357a03dbc298a9ee6bfda06e082e1fd44fa8` 上，修复前已通过实际浏览器完成“不输入原文、不提取、不调用 OCR”的草稿保存和正式建单。因此未复现“纯手工路径一律不可提交”，不能将用户原环境的问题归因于文字/OCR硬性依赖。原报错网页地址、当时错误码/按钮状态仍缺证据；原本机5194→18089预览与最新main不是同一运行版本，本轮未替换它。

确实复现了一个相关恢复缺陷：同一账号向手工草稿接口发送相同请求体及相同 `Idempotency-Key` 两次，原实现忽略该请求头，生成两个草稿。这会在响应丢失后重试时重复建单。本轮修复此问题，并改善缺项提示、明确取消文字导入及异步取消后的状态保护。未改变建单必填、材料、权限、重复检测或状态机规则。

## 当前操作路径与校验

客服进入案件队列 → 新建草稿（或 `/work-orders?create=1`）：

1. 可完全不使用左侧文字、TXT、文件夹、ZIP或OCR辅助。
2. 草稿允许缺项，直接点击“保存草稿”。
3. 正式建单须填写案件号（保险报案号）、车主手机号、车牌或车架号、查勘员姓名、查勘员电话，并选择至少一张符合现有校验的现场物损照片；再点击原“提交正式工单”。
4. 页面持续显示具体缺项；服务端仍执行必填、照片有效性、授权、重复检测、版本及审计校验。车牌格式等原有校验保留。
5. 若实际输入/导入文字，仍须提取、核对冲突并确认；不采用时使用“取消文字导入，保留手填和照片”。取消不撤销已经采用到表单的字段，也不删除已保存来源历史。保存流程已锁定后不能随意改换来源。

事故区县与停车位置属于后续派单阶段校验，本轮未将其新增为正式建单前置条件，也未用停车信息自动补事故区域。详情页可能提示下一步“待派单”尚缺信息，这不表示创建失败。

## API 与恢复语义

`POST /api/v1/work-orders/drafts` 仍仅允许 ADMIN、CUSTOMER_SERVICE。新增可选 `Idempotency-Key` 请求头；当前管理端在同一建单尝试及其重试中复用一个键。

| 情形 | 结果 |
| --- | --- |
| 首次合法手工请求 | 原业务服务创建 MANUAL 草稿及一条创建审计，不创建文字/OCR来源 |
| 同操作者、同键、同请求体 | 返回同一案件的当前状态，不再创建；已正式提交时也返回原案件 |
| 同操作者、同键、不同请求体 | HTTP409，`IDEMPOTENCY_CONFLICT`，要求核对原草稿 |
| 不同操作者使用同一键 | 按操作者隔离，原权限校验仍生效 |
| 不带该头的旧客户端 | 保持原创建接口兼容行为；不承诺其重放幂等性 |

复用既有 `work_order_command` 的请求摘要及事务锁能力，无新增或修改Flyway迁移。创建、命令结果与审计在同一事务提交。摘要不包含明文日志输出；审计不写表单个人资料。

显式删除草稿仍走原权限与草稿状态校验，在同一事务清理该草稿的CREATE_DRAFT命令，避免新增外键引用阻塞原有删除功能；创建和删除审计保留。明确删除结束该草稿及其创建键的恢复生命周期，不承诺删除后使用旧键还能恢复已删除内容。

前端冻结首次手工请求体，响应不明时先用原体/原键恢复案件ID，再将期间修改保存到该草稿。已知ID在后续修改、照片上传或正式提交失败时保留。重试先读取当前状态；已成功提交则不再次上传/提交。连续点击由保存状态拦截。跳转失败保留“已保存”语义，并使用详情地址回退，不能冒充建单失败。

文字读取、提取和候选选择均检查当前编辑代次，取消后到达的旧响应不能重新填表或恢复阻塞。真实未处理冲突仍阻止保存，没有全局忽略确认规则。既有OCR解除关联机制保留，本轮未新增或触发真实识别。
