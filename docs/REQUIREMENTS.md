材料不得在适用节点之前上传；通知单建单起可上传，网点报价和到店照在接单到店对应阶段开放，定损/核损材料须有当前正式报价，进度/完工照只在维修阶段新增。前序补传、替换、冻结和终态按既有规则处理。缺失和角色无权分别返回明确原因。第一批新增管理员/客服只读流程视图，包含节点、当前任务、缺失项和材料有效性，不返回凭页面可绕过的授权。

九节点、绿黄语义、绿勾红叉、文字建单/网点报价OCR/客服核损OCR及玻璃滚动布局见V3；页面与识别链路在第二批实施。资金、投诉独立及既有四角色权限不变。本授权不包含未确认的聊天整包正式写入规则。

本轮新增授权见 D-045：百度真实手写 OCR 为默认关闭的后端配置能力，仅客服明确发起的文档识别可外呼；原始返回、程序候选、人工修订及确认分层保留，确认不写正式业务。第13阶段聊天图片仍不自动 OCR；聊天导入十二项规则见 PHASE13_CONFIRMATION.md，当前待确认。

补充确认：支持尚无案件时客服上传手写单据，识别后自动预填现有草稿字段、对照原图人工修正，再调用既有草稿与正式提交流程。字段映射与禁止推断见 BAIDU_OCR.md；维修明细仅独立候选，维修单号及单据日期不等于报案号及事故时间。真实端到端验收须使用新密钥与隔离测试数据，不能以 Mock 替代。

2026-10-14 页面验收补充：识别入口必须位于原“新建案件草稿”表单内，名为“上传单据识别”，无需先保存案件，也不要求跳往独立 OCR 页面。结果只自动填写当前为空的字段；非空且不同的字段必须逐项让客服选择保留当前值或采用识别值，识别等待期间的人工输入同样受保护。客服对照受控原图修改当前表单，点击保存草稿或提交正式工单后才调用既有业务服务；正式提交继续执行必填、重复检测、权限及审计。识别失败可明确解除本次关联并继续手工建单，不自动重新调用百度。

## 2. 产品定位与目标

平台用于连接平台客服、管理员、维修网点和电动车主，协同处理保险维修案件从建单、派单、报价、核损、维修、交付、投诉到回款和结算记录的全过程。

MVP 的核心目标：

1. 让案件信息、材料、状态和责任人可追踪。
2. 让网点原始报价、平台加价、保险核损和最终结算分层记录并按角色隔离展示。
3. 用明确的授权条件阻止网点在核损确认前开工。
4. 让关键金额、状态和权限操作可审计。
5. 建设可支持十万级以上数据、保留历史版本的正式价格数据库。

## 3. MVP 边界

### 3.1 范围内

- 管理员和客服的电脑网页。
- 维修网点和车主的手机 H5。
- 用户、角色、权限、网点、区域及必要基础数据管理。
- 案件创建、派单、接单、到店、材料上传、OCR、人工校正、报价、核损、维修授权、维修进度、完工、收车、评价、投诉。
- 保险公司回款与网点结算状态/信息记录。
- 站内通知。
- 价格数据库、历史版本和导入批次。
- 操作审计日志。
- 本地 Docker Compose 运行所需的 PostgreSQL 与 MinIO 等依赖。

### 3.2 明确不在第一版范围内

- 保险公司登录或在线确认。
- 车主创建案件、确认报价或支付维修费用。
- 平台内真实收付款、支付通道、自动分账或资金托管。
- 区域经理、财务、客服主管等额外角色。
- 自动确认收车的倒计时和自动执行；仅预留未来扩展空间。
- 真实短信发送；第一版仅站内通知，短信只预留接口。
- 货拉拉接口。
- 真实 OCR 或地图供应商选型与接入；第一版使用 Mock Provider。
- RabbitMQ 或微服务拆分。
- 最终网点结算金额的自动计算规则。

## 4. 角色与职责

| 角色 | 使用端 | 主要职责 | 关键数据限制 |
| --- | --- | --- | --- |
| `ADMIN` | 电脑网页 | 用户、权限、网点、基础数据、投诉工单、系统配置、操作日志 | 可按授权查看管理数据和敏感报价字段 |
| `CUSTOMER_SERVICE` | 电脑网页 | 建单、派单、材料、报价审核与加价、核损录入、维修授权、回款及网点结算记录 | 可查看其工作所需的加价和平台利润 |
| `REPAIR_SHOP` | 手机 H5 | 接单、确认到店、上传材料/报价、维修进度、完工材料和完工提交 | 仅限本店案件；仅见本店原始报价和最终结算信息 |
| `OWNER` | 手机 H5 | 查看本人案件必要进度、确认收车、评价或投诉 | 不得查看报价、加价、平台利润和结算信息 |

保险公司是线下协作方，不是系统角色。其反馈、确认、核损和付款信息由客服录入或导入。

## 5. 端到端核心流程

1. 客服创建工单。
2. 客服选择维修网点并派单。
3. 网点接单并确认车辆到店。
4. 网点或客服上传报价单、配件工时清单和相关照片。
5. 系统调用 OCR Provider 识别文件；MVP 使用 Mock 实现。
6. 有权限的人员人工确认和修正 OCR 结果。
7. 系统生成网点原始报价。
8. 客服审核维修项目。
9. 客服为该报价选择固定金额或百分比之一，对报价总额统一加价。
10. 系统生成平台正式报价。
11. 客服在线下与保险公司沟通。
12. 客服录入保险公司最终核损总额。
13. 客服上传定损单和核损单。
14. 客服勾选“保险公司已确认”并完成平台确认。
15. 满足维修授权条件后开放维修权限。
16. 网点开始维修并持续更新进度。
17. 网点上传必传的完工照片。
18. 网点提交完工。
19. 车主在线确认收车。
20. 车主可选择评价或发起投诉。
21. 投诉生成独立投诉工单，由管理员处理。
22. 客服记录保险公司回款和维修网点结算状态。
23. 工单完成。

上述序列是正常主流程。建单至到店阶段的拒单、取消派单、改派、到店异常、继续等待和取消整个工单规则已经确认，见第 7.5 节和 `WORKFLOW.md`；报价及其后的退回、修订和异常流程仍待对应阶段确认。

## 6. 核心业务规则

### 6.1 报价与加价

- 每张报价只能使用一种加价方式：固定金额或百分比。
- 加价只针对网点原始报价总额，不修改单项配件和工时价格。
- 系统生成并保留网点原始报价与平台正式报价。
- 加价方式、加价值和平台利润仅客服及管理员可见。
- 网点只查看自己的原始报价和最终结算信息。
- 车主不能查看任何报价、加价或结算信息。
- 保险公司最终核损总额由客服人工录入，不得擅自推导或自动覆盖。
- 最终网点结算金额允许为空，由客服人工录入，不自动计算。

### 6.2 维修授权

只有同时满足以下条件，系统才可开放维修权限：

1. 核损单已上传；
2. 最终核损金额已录入；
3. 已记录保险公司确认；
4. 客服已完成平台确认。

无维修授权时，网点不能执行“开始维修”。前端应禁用或隐藏入口，后端仍必须独立拒绝非法请求并记录关键操作。

### 6.3 完工、收车与投诉

- 完工照片在第一版为必传，未满足要求不得提交完工。
- 车主可在线确认收车。
- 自动确认收车仅作为未来扩展点，不设置倒计时、不创建自动执行任务。
- 车主可评价或发起投诉。
- 投诉必须生成独立投诉工单，由管理员处理，不得仅作为普通备注附着在维修工单上。

### 6.4 回款和结算

- 实际资金路径为“保险公司 → 平台 → 维修网点”。
- MVP 只记录保险公司回款和平台对网点结算的信息与状态，不发起真实资金划转。
- 金额字段必须使用 Java `BigDecimal` 和 PostgreSQL `DECIMAL/NUMERIC`，禁止 `float` 或 `double`。

### 6.5 通知和外部能力

- 第一版仅实现站内通知。
- 短信能力只定义可替换接口，不接入真实供应商。
- OCR 定义 `OcrProvider` 并提供 `MockOcrProvider`。
- 地图定义 `MapProvider` 并提供 `MockMapProvider`。
- 货拉拉第一版不接入，也不需要伪造可用页面。

### 6.6 审计

以下操作至少必须保留审计日志：

- 重要金额的新增、修改和状态变化；
- 工单、报价、核损、维修、完工、收车、投诉、回款和结算的关键状态变化；
- 用户角色、权限、网点归属和数据访问范围变化；
- 维修授权的开放、撤销（若后续允许）和被拒绝尝试；
- 重要导入批次及处理结果。

审计日志不得泄露密钥或不必要的敏感个人信息。

## 7. 价格数据库

价格数据库是 MVP 正式功能，不是演示数据表，需支持十万级以上数据与批量导入。

### 7.1 必需数据维度

- 车辆品牌；
- 车型；
- 标准配件；
- 平台内部配件编号；
- 配件别名；
- 适用车型；
- 区域；
- 网点；
- 网点原始报价；
- 平台对外报价；
- 历史保险核损价格；
- 最终网点结算价格；
- 数据来源；
- 生效时间和失效时间；
- 历史版本；
- 导入批次。

### 7.2 历史与性能要求

- 价格更新只能新增版本，不得原地覆盖历史记录。
- 每条价格应能追溯到来源和导入批次（人工录入也应有来源标识）。
- 查询需围绕配件编号/别名、车型、区域、网点、价格类型和有效期建立可验证的索引策略。
- 批量导入需要校验、错误明细和批次结果，不得因单条失败留下不可解释的半成品状态。
- 阶段 3 参考价已确认 CNY、NUMERIC(18,2)；超出两位小数拒绝而非舍入。正式适用优先级仍待业务确认。

### 7.3 阶段 3 已确认范围（2026-10-04）

- 四种独立类型：REPAIR_SHOP_RAW_REFERENCE、PLATFORM_EXTERNAL_REFERENCE、INSURER_HISTORICAL_ASSESSED、REPAIR_SHOP_SETTLEMENT_REFERENCE，不混同或覆盖，不生成案件报价。
- ADMIN 与 CUSTOMER_SERVICE 均可维护品牌、车型、标准配件、别名、配件车型关系，查询价格、新建价格版本、预览/确认导入、查看批次及错误报告。数据来源字典、用户/角色、组织、系统配置及审计管理仍仅 ADMIN；REPAIR_SHOP、OWNER 无价格库权限。运营写入与审计同事务，历史金额、来源和创建信息不可修改或删除，调价只追加版本（D-023）。
- 全国、既有区域、既有网点三种范围并存，返回全部符合条件的候选；禁止自动优先级、回退或加价。
- 品牌、车型、标准配件及全局唯一内部编号、独立别名、多对多车型适配、来源、历史版本、导入批次和错误行；复用阶段 2 组织、用户与审计，只新增迁移。
- XLSX / UTF-8 CSV 解析、校验、预览后显式确认，整批价格原子导入；错误仍可追溯。预览不写正式价格，本阶段不接入对象存储。
- 所有列表分页、稳定排序、单页至多 100；十万条数据由非生产生成器提供，不进入默认迁移。
- 不实现工单、案件、OCR、派单、自动核价、支付或结算流程。

### 7.4 已确认价格版本规则与剩余待确认项

- 已确认：新版本开始日必须晚于当前版本开始日；无期限旧版本在同一事务中补齐截止日为新版本开始日前一天，保留金额、来源、创建信息，并记录审计及版本关联。
- 已确认：所有参考金额必须大于零，CNY NUMERIC(18,2)，额外小数位拒绝而不舍入。
- 已确认：中国自然日 DATE，首尾包含；截止日为空表示持续有效，同一维度不得重叠。手工、预览、正式导入和数据库约束统一执行。
- 正式价格适用优先级仍待业务确认，本阶段不依赖该规则。

### 7.5 阶段 4 已确认的案件、派单与前段状态机规则（2026-10-08）

- 案件使用内部 UUID；只有草稿提交为正式案件时才生成 `EVR-YYYYMMDD-######`，草稿不占号。系统自动填写工单编号、创建客服、创建时间、当前状态、当前负责人和数据来源。
- 正式案件必填保险公司、报案号、事故时间、事故简述、事故城市/区域、车主姓名与手机号、车辆品牌与车型，以及 VIN、车辆牌照、保险认可的其他车辆编号至少一项。报案时间、保单号和详细地址不是正式建单门槛。
- 案件通知单允许在草稿或正式建单后上传；正式建单不要求附件。它在进入报价审核前必须上传，或由客服填写缺失原因，该能力属于提示词 5 以后。
- 强重复为同一保险公司 + 相同报案号，数据库唯一约束禁止第二张正式工单并返回已有工单号。疑似重复包括同 VIN + 相近事故时间、同手机号 + 同车辆 + 相近事故时间、同保单号 + 同车辆，以及同车主 + 同网点 + 短期重复建单；默认 7 天且管理员可配置。继续创建或派单必须填写原因并审计。
- 正式提交按完整手机号精确匹配唯一启用的 OWNER；唯一命中则绑定，未命中或多条命中保持待匹配，不自动开户。
- 正常前段状态为 `DRAFT → PENDING_DISPATCH → PENDING_ACCEPTANCE → PENDING_ARRIVAL → ARRIVED`，另有独立 `ARRIVAL_EXCEPTION`。拒单回到待派单；取消派单保留原记录并回到待派单；到店异常可继续等待、取消派单、改派或取消整个工单。
- 待接单可改派；已接单未到店改派必须确认车辆未到店并填写原因；已到店后仅管理员可异常改派，且必须填写原因和车辆转运说明。系统不提供通用“回退上一状态”。
- 正式工单不能物理删除，只能取消或关闭；取消必须填写原因、说明及是否通知车主和网点。已到店或已产生报价后只有管理员可取消，取消后禁止继续业务操作。
- 管理员和客服按业务需要查看完整案件；草稿仅创建客服和管理员可见。当前网点列表默认脱敏，授权详情才显示维修联系所需信息；未派单网点不能查询案件；车主只能查看绑定本人的案件。
- 所有状态操作使用 `Idempotency-Key`、事务、工单乐观锁和 assignment_version；重复请求返回第一次结果且不重复生成历史、审计或派单。接单和到店还支持同网点、同版本的语义重复成功；旧派单、其他网点或已取消派单拒绝。
- 本阶段不实现文件/MinIO、OCR、地图、报价、核损、维修授权或后续流程；这些从提示词 5 开始。

## 8. 工程与质量要求

- 管理端：Vue 3 + TypeScript + Vite + Element Plus。
- 网点/车主 H5：Vue 3 + TypeScript + Vite + Vant。
