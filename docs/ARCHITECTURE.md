# 电动车保险维修案件协同平台 MVP 架构说明

## 1. 架构目标

在不引入微服务复杂度的前提下，为四类用户提供职责清晰、可审计、可扩展的案件协作系统，并满足以下关键质量属性：

- 安全：角色、网点/本人数据范围及敏感字段三层隔离。
- 一致性：状态、金额与审计记录在清晰事务边界内变更。
- 可追溯：报价和价格版本不覆盖历史，关键操作有审计。
- 可维护：按业务领域组织，避免技术分层形成巨型目录。
- 可部署：本地 Docker Compose 可复现，应用配置可迁移到云环境。
- 可验证：所有层次具备自动化测试入口和阶段质量门禁。

## 2. 系统上下文

```text
管理员 / 客服（电脑浏览器） ──> 管理端 Vue 应用 ──┐
                                                     │ REST / JSON / JWT
维修网点 / 车主（手机浏览器） ──> H5 Vue 应用 ─────┤
                                                     v
                                          Spring Boot 模块化单体
                                           │        │        │
                                      PostgreSQL  MinIO   Provider 接口
                                           │                 │
                                      业务数据/任务表       Mock OCR/地图/短信
```

保险公司在系统边界外，由客服将线下确认、核损及回款信息录入或导入。系统记录资金状态，不连接真实支付网络。

## 3. 逻辑组件

### 3.1 前端

建议在同一仓库维护两个独立应用：

- `admin-web`：管理员与客服的桌面网页，Vue 3 + TypeScript + Vite + Element Plus。
- `h5-web`：网点与车主的移动网页，Vue 3 + TypeScript + Vite + Vant；登录后按角色进入不同功能。

两个应用独立构建，减少桌面组件库与移动组件库互相污染。初期不建立复杂共享组件包；可共享 OpenAPI 生成的类型或极少量无 UI 工具，但需等实际重复出现后再提取。

前端负责交互层权限提示和字段隐藏，不能作为安全边界。所有权限、数据范围、状态门禁由后端再次校验。

### 3.2 后端模块化单体

后端保持一个可部署应用，在代码内按业务领域划分模块。建议的领域边界如下，最终包名在初始化阶段确定：

| 领域 | 主要职责 |
| --- | --- |
| identity-access | 账号、认证、JWT、角色、权限和数据范围 |
| organization | 区域、维修网点及归属关系 |
| work-order | 建单、派单、接单、到店和工单主状态 |
| document | 文件元数据、业务附件关系、对象存储访问控制 |
| quotation | OCR 结果确认、维修项目、原始报价、加价和正式报价 |
| pricing | 品牌、车型、配件、别名、适配关系、价格版本和导入批次 |
| assessment | 保险核损金额、定损/核损材料、确认与维修授权 |
| repair | 开工、维修进度、完工照片和完工提交 |
| delivery | 车主收车确认与评价 |
| complaint | 独立投诉工单及管理员处理 |
| settlement | 保险回款和网点结算记录，不执行真实资金划转 |
| notification | 站内通知及未来短信端口 |
| audit | 关键操作审计、追踪与受控查询 |
| async-job | PostgreSQL 任务表、重试、定时 Worker |
| integration | `ObjectStorageService`、`OcrProvider`、`MapProvider` 等适配器 |

每个领域内部只在必要时使用类似 `api`、`application`、`domain`、`infrastructure` 的职责划分。领域依赖通过应用服务或明确接口连接，禁止 Controller 直接拼接跨领域 Mapper。

### 3.3 数据与基础设施

- PostgreSQL：事务型业务数据、价格库、审计索引和异步任务表。
- MinIO：本地附件对象存储；数据库保存文件元数据、对象键、校验信息和业务关联。
- Flyway：唯一数据库结构演进通道。
- MyBatis-Plus：常规、明确的单表 CRUD 和分页。
- MyBatis XML：复杂查询、批量导入/更新、报表式读取和需要精确 SQL 调优的场景。
- OpenAPI/Swagger：接口契约和调试入口。

## 4. 请求与安全模型

### 4.1 认证与授权

1. 用户通过账号和密码登录；密码为数据库 BCrypt 哈希。
2. 后端签发有期限的 JWT；Token 只携带最小身份声明，不把可变权限永久固化在长生命周期 Token 中。
3. Spring Security 完成认证，RBAC 判断功能权限。
4. 应用服务继续校验数据范围：网点只能访问本店案件，车主只能访问本人关联案件。
5. DTO/查询投影执行字段级隔离，避免先读取全部敏感字段再依赖前端隐藏。

管理员拥有管理职责并不意味着所有接口无条件放行；具体权限点仍应显式配置和审计。

### 4.2 API 约定

所有 API 使用版本化 REST 路径。统一响应至少表达：业务码、消息、数据和请求追踪标识；分页数据至少表达当前页、每页数量、总数和记录列表。精确字段名在项目初始化阶段固化后写入 OpenAPI。

统一异常处理覆盖：参数校验、未认证、无权限、资源不存在、业务状态冲突、重复/幂等冲突和不可预期错误。服务端日志保留详细上下文，客户端只收到安全且可定位的错误信息。

### 4.3 状态门禁

工单的核心动作使用显式状态转换，不允许任意更新状态字段。维修授权是后端计算并持久化/记录的关键业务事件；只有核损单存在、保险确认已记录、客服确认已完成时才可开放。开始维修时再次验证授权，防止旧页面或直接调用 API 绕过。

## 5. 数据架构要点

### 5.1 金额模型

- Java：只用 `BigDecimal`。
- PostgreSQL：只用带明确精度和小数位的 `NUMERIC/DECIMAL`。
- API：金额使用十进制字符串或经过验证的十进制表示，避免 JavaScript 二进制浮点参与运算。
- 舍入模式、金额精度、百分比精度和币种在对应阶段确认，不能由实现者默认。

原始报价、平台加价、平台正式报价、保险核损、保险回款和网点结算是不同业务概念，分别存储和审计，不用一个可变“最终金额”字段反复覆盖。

### 5.2 价格数据库

价格库采用“稳定主数据 + 不可变价格版本 + 导入批次”的关系模型：

- 稳定主数据：品牌、车型、标准配件、平台配件编号、别名、区域、网点、车型适配关系。
- 价格事实：价格类型、金额、适用维度、来源、生效/失效时间、版本和批次引用。
- 导入批次：文件/来源、发起人、状态、总数、成功数、失败数、校验错误摘要和时间。
- 业务快照：案件报价引用当时的价格或保存必要快照，后续价格版本变化不得改变历史案件金额。

阶段 3 用户指令要求历史价格行不可修改或删除，包括金额和有效期；调价只能新增版本且不能重叠。无失效时间旧版本的后续调价方式及时间区间口径待确认，不沿用早期“直接结束旧行有效期”的描述。逻辑价格主键为标准配件、车型、价格类型、适用范围（全国 / region_id / shop_id），生效开始时间区分版本，内部配件编号全局唯一；正式价格适用优先级尚待业务确认，只返回候选记录。

本次先新增 V3 目录迁移（既有 V1、V2、V2.1 原样保留）：price_brand、price_model（brand_id + code 唯一）、price_part（internal_code 全局唯一）、price_alias（part_id + name 唯一、别名可指向多个配件）、price_part_model（复合主键）、price_source（code 唯一，来源类型为 MANUAL / CSV / EXCEL / HISTORICAL_CASE）。全部维护写入既有审计；删除有引用的主数据通过外键拒绝，禁止级联删除。

单表 CRUD 使用 MyBatis-Plus，适配和组织只读投影使用 XML。所有查询分页并以 ID / 复合 ID 稳定排序，单页最多 100；内部编号精确查询走唯一索引，别名和配件名称使用转义通配符的前缀查询及 pattern_ops 索引；车型品牌和适配关系具备双向索引。区域、网点、服务区域复用既有表，客服仅能读取 ID/编码/名称投影，不开放联系方式或组织维护。

价格版本、导入与十万条价格验证尚未落地；金额范围和时间区间确认后才建立对应约束，不能将目录测试记作十万条价格验证。CNY 参考金额已确认 NUMERIC(18,2)，超出精度拒绝，不静默舍入。导入仅临时解析文件，不接入对象存储、不实现案件业务。

### 5.3 文件模型

业务表不直接保存本地路径或公开 URL。文件元数据记录对象键、原始文件名、媒体类型、大小、校验值、上传者、归属业务对象和访问级别。下载由后端鉴权后返回受控内容或短期访问地址。

### 5.4 审计模型

审计记录至少包含操作者、角色、动作、对象类型与标识、关键变更前后摘要、发生时间和追踪标识。金额、状态、权限和导入操作必须覆盖。审计写入与关键业务变更应处于可靠的一致性边界，普通业务角色不得修改或删除审计记录。

## 6. 外部能力与异步任务

### 6.1 Provider 端口

- `ObjectStorageService`：上传、读取、删除/归档和受控访问；本地实现对接 MinIO。
- `OcrProvider`：提交识别请求并返回结构化识别结果；MVP 为 `MockOcrProvider`。
- `MapProvider`：地址解析/地图能力的最小契约；MVP 为 `MockMapProvider`，具体用例确认后再定方法。
- 短信端口：只保留清晰接口和不可误认为真实发送的测试实现；MVP 用户可见通知走站内通知。

业务模块依赖接口，不直接依赖供应商 SDK，后续替换供应商时不改核心业务规则。

### 6.2 PostgreSQL 任务表

异步任务记录类型、载荷引用、状态、计划执行时间、尝试次数、锁定信息和最后错误。多个 Worker 通过数据库行锁（实现阶段评估 `FOR UPDATE SKIP LOCKED`）竞争任务，处理器必须幂等，并设置有限重试与失败可观测性。

它适合 MVP 的有限吞吐和单数据库运维模式；若未来出现高吞吐、复杂路由或严格事件流需求，再以指标为依据评估消息队列。

## 7. 部署与配置

本地 Docker Compose 负责 PostgreSQL、MinIO 等基础依赖；前后端可按开发体验选择宿主机运行，最终提供完整启动说明。应用镜像保持无状态，运行配置通过环境变量注入。

环境分层至少包括 local/test 和未来 production。仓库提交 `.env.example`，不提交 `.env` 中的真实秘密。健康检查区分应用存活与依赖就绪。数据库备份、MinIO 数据保护、HTTPS、域名和云服务映射在上线加固阶段确定。

## 8. 测试策略

- 单元测试：金额计算、状态转换、权限判断、价格版本规则。
- 数据库集成测试：Flyway、Mapper、分页、唯一/外键约束、任务并发领取。
- API 集成测试：统一响应、异常映射、JWT/RBAC、跨网点/跨车主越权。
- 前端测试：关键表单规则、字段可见性、状态门禁和主要流程组件。
- 端到端冒烟：四类角色贯穿正常主流程。
- 性能验证：十万级价格导入、检索、分页和关键组合筛选。
- 构建门禁：后端 test/package；前端 lint/typecheck/test/build；Compose 配置与健康检查。

## 9. 技术栈选择：理由、优势与劣势

| 技术选择 | 选择理由与优势 | 劣势与控制方式 |
| --- | --- | --- |
| Vue 3 + TypeScript + Vite | 组件生态成熟；Composition API 适合复杂表单和流程；TS 提前发现接口/状态错误；Vite 开发与构建反馈快 | 两个前端应用会有少量重复；TS 与构建工具需要统一规范。先保持应用独立，重复真实出现后再抽共享代码 |
| Element Plus（管理端） | 表格、表单、分页、上传等后台场景组件齐全，能快速交付一致的桌面体验 | 默认样式较通用、包体较大；通过按需引入、设计变量和业务组件控制，不做无关深度定制 |
| Vant（H5） | 面向移动端，触控、表单、上传与反馈组件成熟，适合网点和车主 H5 | 不适合复杂桌面表格；因此与管理端分应用，不混用组件库 |
| Java 21 + Spring Boot 3.5 | Java 21 是 LTS，类型与生态稳定；Spring Boot/Security 适合事务、权限、审计和企业集成；团队后续招聘与维护成本可控 | 启动和内存高于轻量运行时，框架配置有复杂度；用模块化单体、清晰依赖和有限组件控制成本 |
| Spring Security + JWT + RBAC | 服务端认证授权能力成熟；JWT 适合前后端分离；RBAC 与四类固定角色匹配 | Token 撤销与权限实时变更需要设计；RBAC 本身不解决网点/本人数据范围。使用 30 分钟有效期、过期重新登录（无刷新 Token），每次请求检查数据库状态，并在应用层做数据范围校验 |
| PostgreSQL | 强事务、约束、索引和 `NUMERIC` 适合金额与状态一致性；复杂查询和批量能力可支撑正式价格库；还能承载 MVP 任务表 | 单库会成为容量和故障集中点；需索引、备份、连接池和监控，未来依据数据再扩展而非提前分库 |
| MyBatis-Plus + MyBatis XML | 简单 CRUD 少样板，复杂价格/报表查询仍能完全控制 SQL 和执行计划 | 两套写法增加规范成本，XML 与对象变更可能不同步；明确使用边界并用数据库集成测试约束 |
| Flyway | 迁移可版本化、可审查、各环境结果一致，避免自动建表导致结构漂移 | 已执行迁移不能随意修改，冲突需要纪律；采用只追加迁移和阶段验证 |
| REST + OpenAPI/Swagger | 浏览器客户端兼容好，契约清晰，便于联调、测试和生成类型 | 契约与代码可能漂移、接口演进需管理；构建中校验 OpenAPI 并采用版本化路径 |
| MinIO + `ObjectStorageService` | 本地具备 S3 风格对象存储，文件不挤占数据库；接口隔离便于未来迁移云对象存储 | 多一个服务需运维，数据库与对象存储存在跨系统一致性问题；用元数据状态、补偿清理和受控对象键管理 |
| Provider + Mock OCR/地图 | 在供应商未选型时仍可完成流程与自动化测试，核心业务不绑定厂商 | Mock 无法证明真实识别质量、延迟和费用；上线真实集成前必须增加契约、失败与性能测试 |
| PostgreSQL 任务表 + Worker | 无需引入消息中间件，事务可与业务数据协调，部署简单，符合 MVP 吞吐 | 轮询增加数据库负载，吞吐/路由能力不如消息队列；设置索引、批量领取、退避和指标，达到阈值后再评估迁移 |
| Docker Compose | 本地依赖版本一致、启动方式可文档化，为容器化云部署打基础 | 不是生产编排和高可用方案；生产的编排、密钥、备份和伸缩另行设计 |
| 模块化单体 | 单一部署、同库事务、调试和运维简单，同时用领域模块保持边界，最适合 MVP | 模块边界若不约束会退化为大泥球，不能独立扩缩；通过包边界、依赖测试和领域 API 约束 |

总体取舍是以成熟生态、强事务和低运维复杂度换取一定的进程体量与单库耦合。对当前团队规模和 MVP 流程一致性要求，这比微服务和消息队列的额外分布式成本更合适。

## 10. 已知架构风险

- 当前本机 Java 版本与目标 Java 21 不一致，Maven 未安装；进入后端初始化前需补齐或采用 Maven Wrapper 并用 JDK 21 验证。
- Docker CLI/Compose 已安装，但守护进程当前未运行；基础设施阶段需启动 Docker Desktop 后验证。
- 报价总额加价但单项价格不变会产生“正式总额与明细合计关系”的展示问题，需在报价阶段前确认。
- JWT 每请求读取实时账号状态；数据库不可用时认证不能继续。阶段 2 登录与生命周期规则见 D-018。
- PostgreSQL 任务表与价格库共享数据库，需要用指标防止 Worker 或批量导入影响在线请求。
