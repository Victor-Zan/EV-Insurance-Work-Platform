# 电动车保险维修案件协同平台 MVP 架构说明

## 1. 架构目标

在不引入微服务复杂度的前提下，为四类用户提供职责清晰、可审计、可扩展的案件协作系统，并满足以下关键质量属性：

- 安全：角色、网点/本人数据范围及敏感字段三层隔离。
- 一致性：状态、金额与审计记录在清晰事务边界内变更。
- 可追溯：报价和价格版本不覆盖历史，关键操作有审计。
- 可维护：按业务领域组织，避免技术分层形成巨型目录。
- 可部署：本地 Docker Compose 可复现，应用配置可迁移到云环境。
- 可验证：所有层次具备自动化测试入口和阶段质量门禁。

## 2. 系统上下文

```text
管理员 / 客服（电脑浏览器） ──> 管理端 Vue 应用 ──┐
                                                     │ REST / JSON / JWT
维修网点 / 车主（手机浏览器） ──> H5 Vue 应用 ─────┤
                                                     v
                                          Spring Boot 模块化单体
                                           │        │        │
                                      PostgreSQL  MinIO   Provider 接口
                                           │                 │
                                      业务数据/任务表       Mock OCR/地图/短信
```

保险公司在系统边界外，由客服将线下确认、核损及回款信息录入或导入。系统记录资金状态，不连接真实支付网络。

## 3. 逻辑组件

### 3.1 前端

建议在同一仓库维护两个独立应用：

- `admin-web`：管理员与客服的桌面网页，Vue 3 + TypeScript + Vite + Element Plus。
- `h5-web`：网点与车主的移动网页，Vue 3 + TypeScript + Vite + Vant；登录后按角色进入不同功能。

两个应用独立构建，减少桌面组件库与移动组件库互相污染。初期不建立复杂共享组件包；可共享 OpenAPI 生成的类型或极少量无 UI 工具，但需等实际重复出现后再提取。

前端负责交互层权限提示和字段隐藏，不能作为安全边界。所有权限、数据范围、状态门禁由后端再次校验。

### 3.2 后端模块化单体

后端保持一个可部署应用，在代码内按业务领域划分模块。建议的领域边界如下，最终包名在初始化阶段确定：

| 领域 | 主要职责 |
| --- | --- |
| identity-access | 账号、认证、JWT、角色、权限和数据范围 |
| organization | 区域、维修网点及归属关系 |
| work-order | 建单、派单、接单、到店和工单主状态 |
| document | 文件元数据、业务附件关系、对象存储访问控制 |
| quotation | OCR 结果确认、维修项目、原始报价、加价和正式报价 |
| pricing | 品牌、车型、配件、别名、适配关系、价格版本和导入批次 |
| assessment | 保险核损金额、定损/核损材料、确认与维修授权 |
| repair | 开工、维修进度、完工照片和完工提交 |
| delivery | 车主收车确认与评价 |
| complaint | 独立投诉工单及管理员处理 |
| settlement | 保险回款和网点结算记录，不执行真实资金划转 |
| notification | 站内通知及未来短信端口 |
| audit | 关键操作审计、追踪与受控查询 |
| async-job | PostgreSQL 任务表、重试、定时 Worker |
| integration | `ObjectStorageService`、`OcrProvider`、`MapProvider` 等适配器 |

每个领域内部只在必要时使用类似 `api`、`application`、`domain`、`infrastructure` 的职责划分。领域依赖通过应用服务或明确接口连接，禁止 Controller 直接拼接跨领域 Mapper。

### 3.3 数据与基础设施

- PostgreSQL：事务型业务数据、价格库、审计索引和异步任务表。
- MinIO：本地附件对象存储；数据库保存文件元数据、对象键、校验信息和业务关联。
- Flyway：唯一数据库结构演进通道。
- MyBatis-Plus：常规、明确的单表 CRUD 和分页。
- MyBatis XML：复杂查询、批量导入/更新、报表式读取和需要精确 SQL 调优的场景。
- OpenAPI/Swagger：接口契约和调试入口。

## 4. 请求与安全模型

### 4.1 认证与授权

1. 用户通过账号和密码登录；密码为数据库 BCrypt 哈希。
2. 后端签发有期限的 JWT；Token 只携带最小身份声明，不把可变权限永久固化在长生命周期 Token 中。
3. Spring Security 完成认证，RBAC 判断功能权限。
4. 应用服务继续校验数据范围：网点只能访问本店案件，车主只能访问本人关联案件。
5. DTO/查询投影执行字段级隔离，避免先读取全部敏感字段再依赖前端隐藏。

管理员拥有管理职责并不意味着所有接口无条件放行；具体权限点仍应显式配置和审计。

### 4.2 API 约定

所有 API 使用版本化 REST 路径。统一响应至少表达：业务码、消息、数据和请求追踪标识；分页数据至少表达当前页、每页数量、总数和记录列表。精确字段名在项目初始化阶段固化后写入 OpenAPI。

统一异常处理覆盖：参数校验、未认证、无权限、资源不存在、业务状态冲突、重复/幂等冲突和不可预期错误。服务端日志保留详细上下文，客户端只收到安全且可定位的错误信息。

### 4.3 状态门禁

工单的核心动作使用显式状态转换，不允许任意更新状态字段。维修授权是后端计算并持久化/记录的关键业务事件；只有核损单存在、最终核损金额已录入、保险确认已记录、客服确认已完成时才可开放。开始维修时再次验证授权，防止旧页面或直接调用 API 绕过。

## 5. 数据架构要点

### 5.1 金额模型

- Java：只用 `BigDecimal`。
- PostgreSQL：只用带明确精度和小数位的 `NUMERIC/DECIMAL`。
- API：金额使用十进制字符串或经过验证的十进制表示，避免 JavaScript 二进制浮点参与运算。
- 舍入模式、金额精度、百分比精度和币种在对应阶段确认，不能由实现者默认。

原始报价、平台加价、平台正式报价、保险核损、保险回款和网点结算是不同业务概念，分别存储和审计，不用一个可变“最终金额”字段反复覆盖。

### 5.2 价格数据库

价格库采用“稳定主数据 + 不可变价格版本 + 导入批次”的关系模型：

- 稳定主数据：品牌、车型、标准配件、平台配件编号、别名、区域、网点、车型适配关系。
- 价格事实：价格类型、金额、适用维度、来源、生效/失效时间、版本和批次引用。
- 导入批次：文件/来源、发起人、状态、总数、成功数、失败数、校验错误摘要和时间。
- 业务快照：案件报价引用当时的价格或保存必要快照，后续价格版本变化不得改变历史案件金额。

阶段 3 已确认规则见 D-021：逻辑价格主键为标准配件、车型、价格类型、适用范围（NATIONAL / REGION + region_id / SHOP + shop_id）。price_record 使用 UNIQUE NULLS NOT DISTINCT，保证全国范围的空组织键也唯一。内部配件编号全局唯一，价格须关联已配置的配件/车型关系。四种价格类型分别保存，不自动生成案件金额。

本次先新增 V3 目录迁移（既有 V1、V2、V2.1 原样保留）：price_brand、price_model（brand_id + code 唯一）、price_part（internal_code 全局唯一）、price_alias（part_id + name 唯一、别名可指向多个配件）、price_part_model（复合主键）、price_source（code 唯一，来源类型为 MANUAL / CSV / EXCEL / HISTORICAL_CASE）。全部维护写入既有审计；删除有引用的主数据通过外键拒绝，禁止级联删除。

单表 CRUD 使用 MyBatis-Plus，适配和组织只读投影使用 XML。所有查询分页并以 ID / 复合 ID 稳定排序，单页最多 100；内部编号精确查询走唯一索引，别名和配件名称使用转义通配符的前缀查询及 pattern_ops 索引；车型品牌和适配关系具备双向索引。区域、网点、服务区域复用既有表，客服仅能读取 ID/编码/名称投影，不开放联系方式或组织维护。

新增 V4 保存 price_record、price_version、预览暂存、导入批次与错误明细；未修改 V1/V2/V2.1/V3。价格为正数 CNY NUMERIC(18,2)，Java BigDecimal，响应金额为字符串；API 和导入拒绝额外小数位，不舍入。有效期是 DATE / LocalDate 中国自然日，首尾包含，空截止日表示持续有效。

版本按同一逻辑主键递增，唯一键为 record_id + version_no，另约束 record_id + effective_from 唯一。新开始日必须晚于最新开始日；有限旧区间不缩短、不覆盖。新增版本与无期限前序的截止日补齐（新开始日前一天）在同一事务内完成，previous_version_id / closed_by_version_id 保留双向追溯，并写既有审计。来源代码、名称、类型保存快照，历史金额、来源及创建信息不能修改或删除。

PriceRules 同时服务手工维护和 ImportValidator；手工与批量导入最终复用 PriceMapper.apply。逻辑主键排序后获取事务 advisory lock，数据库触发器再锁 price_record，校验连续版本及来源快照。原生 int8range + daterange GiST 排他约束拒绝同维度区间重叠，不要求 btree_gist 扩展；延迟约束校验截止日与关联后继的下一日关系。数据库触发器禁止价格维度修改、历史字段更新与删除，只允许受控补齐无期限截止日。

候选查询按价格版本 ID 倒序稳定分页，最多 100 条。支持内部编号/别名精确查询、品牌、车型、价格类型、范围、区域、网点及适用日；不传日期可查历史。区域条件返回全国、该区域及服务该区域的网点候选；网点条件返回全国、该网点及其服务区域候选。两个条件同时提供时取条件交集，可用 scope 显式收窄；不推断父子区域，不排序选出“最终价”。正式价格适用优先级仍待业务确认。

索引：V3 的内部编号唯一索引、别名名称索引、车型品牌索引及适配关系双向索引；V4 的 part/type/model 和 model/type/part 组合索引、区域/网点部分索引、类型与范围索引、record/version、日期 GiST、导入批次索引。十万条真实 PostgreSQL 测试验证分页及常用筛选；内部编号计划使用 price_part_internal_code_key → idx_price_record_part_type → idx_price_version_record，别名计划使用 idx_price_alias_name → idx_price_record_part_type。选择性低的筛选是否使用索引由优化器决定，不承诺固定耗时。

导入采用有界流式文件解析（CSV 逐行、XLSX SAX），最多 10 MiB / 20,000 行 / 单元格 256 字符；XLSX 解压条目最多 16 MiB、文本上限 10 MiB，保留 POI 压缩比保护。文件仅临时存在并删除，保存 SHA-256、创建者专属的 30 分钟预览、原始字段及错误上下文，不接入对象存储。预览不写正式价格；确认后重新校验并按维度/日期排序，同批可追加多个版本。重复开始日、有限区间重叠或任意错误整批价格零写入；并发数据库冲突回滚价格与截止审计后，单独记录失败批次/错误。重复确认同一预览返回原批次。模板和操作说明见 [PRICE_IMPORT.md](PRICE_IMPORT.md)。

所有价格管理写入与审计同事务。依据 D-023，ADMIN 与 CUSTOMER_SERVICE 均可维护品牌/车型/配件/别名/适配，查询价格及历史、创建版本、预览/确认导入、查询批次与错误报告；导入预览新增审计动作并保存 UUID 对象标识，预览仍仅创建者可访问/确认。数据来源字典维护、用户/角色/组织/系统配置和审计管理仅 ADMIN，来源快照与历史字段保护不变。组织只读投影不泄露联系方式；复用阶段 2 每请求身份校验、401/403 及 traceId。管理端同步角色按钮及路由控制，来源字典按钮单独限管理员，H5 无价格入口。本次仅授权及审计代码调整，不修改任何迁移。

### 5.3 阶段 4 案件与派单模型

`work_order` 使用 UUID 主键，展示编号由按中国业务日期原子更新的 `work_order_number_counter` 生成。草稿允许业务字段不完整且无展示编号；正式提交在同一事务完成必填校验、重复提示确认、车主匹配、编号生成、状态历史和审计。保险通知书不是正式提交门槛。正式案件的保险公司 + 报案号由部分唯一索引兜底。

工单主表保存当前状态、当前负责人和当前网点投影，`work_order_assignment` 按案件保存不可覆盖的指派版本及接单、拒单、取消信息；`work_order_status_history` 保存动作、前后状态、原因、操作者角色、指派版本和 traceId。所有动作先锁案件并校验版本/状态，幂等命令表保存操作者 + 操作 + Idempotency-Key 对应的第一次响应。数据库状态枚举包含完整已知状态，但阶段 4 只开放到 ARRIVED 的转换及到店前异常/取消分支，不开放报价、核损或维修接口。

数据范围由查询和应用服务双重限制：管理员可查看全部，客服只看本人草稿和全部正式案件，网点仅当前指派给本店的案件，车主仅 owner_user_id 绑定本人。网点列表投影对姓名、手机号、车辆编号等脱敏并省略详细地址和事故描述，授权详情才返回维修联系所需信息。到店异常进入独立 `ARRIVAL_EXCEPTION`，随后只允许继续等待、取消派单、改派或取消整个工单。

### 5.4 文件模型

文件能力从提示词 5 开始实现。目标模型仍要求业务表不保存本地路径或公开 URL；文件内容经 `ObjectStorageService` 访问，数据库只保存元数据与受控对象键，下载必须经过后端鉴权。阶段 4 不创建文件表、不接入 MinIO 客户端，也不把任何附件设为正式建单或确认到店的门槛。

### 5.5 审计模型

审计记录至少包含操作者、角色、动作、对象类型与标识、关键变更前后摘要、发生时间和追踪标识。金额、状态、权限和导入操作必须覆盖。审计写入与关键业务变更应处于可靠的一致性边界，普通业务角色不得修改或删除审计记录。

## 6. 外部能力与异步任务

### 6.1 Provider 端口

- `ObjectStorageService`：上传、读取、删除/归档和受控访问；本地实现对接 MinIO。
- `OcrProvider`：提交识别请求并返回结构化识别结果；MVP 为 `MockOcrProvider`。
- `MapProvider`：地址解析/地图能力的最小契约；MVP 为 `MockMapProvider`，具体用例确认后再定方法。
- 短信端口：只保留清晰接口和不可误认为真实发送的测试实现；MVP 用户可见通知走站内通知。

业务模块依赖接口，不直接依赖供应商 SDK，后续替换供应商时不改核心业务规则。

上述 Provider 均是后续阶段目标边界。阶段 4 不创建 `ObjectStorageService`、`OcrProvider` 或 `MapProvider` 实现；进入提示词 5 后再按已确认文件、OCR 与地图规则落地。

### 6.2 PostgreSQL 任务表

异步任务记录类型、载荷引用、状态、计划执行时间、尝试次数、锁定信息和最后错误。多个 Worker 通过数据库行锁（实现阶段评估 `FOR UPDATE SKIP LOCKED`）竞争任务，处理器必须幂等，并设置有限重试与失败可观测性。

它适合 MVP 的有限吞吐和单数据库运维模式；若未来出现高吞吐、复杂路由或严格事件流需求，再以指标为依据评估消息队列。

## 7. 部署与配置

本地 Docker Compose 负责 PostgreSQL、MinIO 等基础依赖；前后端可按开发体验选择宿主机运行，最终提供完整启动说明。应用镜像保持无状态，运行配置通过环境变量注入。

环境分层至少包括 local/test 和未来 production。仓库提交 `.env.example`，不提交 `.env` 中的真实秘密。健康检查区分应用存活与依赖就绪。数据库备份、MinIO 数据保护、HTTPS、域名和云服务映射在上线加固阶段确定。

## 8. 测试策略

- 单元测试：金额计算、状态转换、权限判断、价格版本规则。
- 数据库集成测试：Flyway、Mapper、分页、唯一/外键约束、任务并发领取。
- API 集成测试：统一响应、异常映射、JWT/RBAC、跨网点/跨车主越权。
- 前端测试：关键表单规则、字段可见性、状态门禁和主要流程组件。
- 端到端冒烟：四类角色贯穿正常主流程。
- 性能验证：十万级价格导入、检索、分页和关键组合筛选。
- 构建门禁：后端 test/package；前端 lint/typecheck/test/build；Compose 配置与健康检查。

## 9. 技术栈选择：理由、优势与劣势

| 技术选择 | 选择理由与优势 | 劣势与控制方式 |
| --- | --- | --- |
| Vue 3 + TypeScript + Vite | 组件生态成熟；Composition API 适合复杂表单和流程；TS 提前发现接口/状态错误；Vite 开发与构建反馈快 | 两个前端应用会有少量重复；TS 与构建工具需要统一规范。先保持应用独立，重复真实出现后再抽共享代码 |
| Element Plus（管理端） | 表格、表单、分页、上传等后台场景组件齐全，能快速交付一致的桌面体验 | 默认样式较通用、包体较大；通过按需引入、设计变量和业务组件控制，不做无关深度定制 |
| Vant（H5） | 面向移动端，触控、表单、上传与反馈组件成熟，适合网点和车主 H5 | 不适合复杂桌面表格；因此与管理端分应用，不混用组件库 |
| Java 21 + Spring Boot 4.1.1 | Java 21保留；用户确认迁移至Boot4路线，采用Framework7、Boot4 starter、Jackson3、MP Boot4 starter及springdoc3.1.1 | 主版本迁移单独回归身份/价格/工单/幂等快照与迁移，业务开发不混入财务或状态机变更 |
| Spring Security + JWT + RBAC | 服务端认证授权能力成熟；JWT 适合前后端分离；RBAC 与四类固定角色匹配 | Token 撤销与权限实时变更需要设计；RBAC 本身不解决网点/本人数据范围。使用 30 分钟有效期、过期重新登录（无刷新 Token），每次请求检查数据库状态，并在应用层做数据范围校验 |
| PostgreSQL | 强事务、约束、索引和 `NUMERIC` 适合金额与状态一致性；复杂查询和批量能力可支撑正式价格库；还能承载 MVP 任务表 | 单库会成为容量和故障集中点；需索引、备份、连接池和监控，未来依据数据再扩展而非提前分库 |
| MyBatis-Plus + MyBatis XML | 简单 CRUD 少样板，复杂价格/报表查询仍能完全控制 SQL 和执行计划 | 两套写法增加规范成本，XML 与对象变更可能不同步；明确使用边界并用数据库集成测试约束 |
| Flyway | 迁移可版本化、可审查、各环境结果一致，避免自动建表导致结构漂移 | 已执行迁移不能随意修改，冲突需要纪律；采用只追加迁移和阶段验证 |
| REST + OpenAPI/Swagger | 浏览器客户端兼容好，契约清晰，便于联调、测试和生成类型 | 契约与代码可能漂移、接口演进需管理；构建中校验 OpenAPI 并采用版本化路径 |
| MinIO + `ObjectStorageService` | 本地具备 S3 风格对象存储，文件不挤占数据库；接口隔离便于未来迁移云对象存储 | 多一个服务需运维，数据库与对象存储存在跨系统一致性问题；用元数据状态、补偿清理和受控对象键管理 |
| Provider + Mock OCR/地图 | 在供应商未选型时仍可完成流程与自动化测试，核心业务不绑定厂商 | Mock 无法证明真实识别质量、延迟和费用；上线真实集成前必须增加契约、失败与性能测试 |
| PostgreSQL 任务表 + Worker | 无需引入消息中间件，事务可与业务数据协调，部署简单，符合 MVP 吞吐 | 轮询增加数据库负载，吞吐/路由能力不如消息队列；设置索引、批量领取、退避和指标，达到阈值后再评估迁移 |
| Docker Compose | 本地依赖版本一致、启动方式可文档化，为容器化云部署打基础 | 不是生产编排和高可用方案；生产的编排、密钥、备份和伸缩另行设计 |
| 模块化单体 | 单一部署、同库事务、调试和运维简单，同时用领域模块保持边界，最适合 MVP | 模块边界若不约束会退化为大泥球，不能独立扩缩；通过包边界、依赖测试和领域 API 约束 |

总体取舍是以成熟生态、强事务和低运维复杂度换取一定的进程体量与单库耦合。对当前团队规模和 MVP 流程一致性要求，这比微服务和消息队列的额外分布式成本更合适。

## 10. 已知架构风险

- 当前本机 Java 版本与目标 Java 21 不一致，Maven 未安装；进入后端初始化前需补齐或采用 Maven Wrapper 并用 JDK 21 验证。
- Docker CLI/Compose 已安装，但守护进程当前未运行；基础设施阶段需启动 Docker Desktop 后验证。
- 报价总额加价但单项价格不变会产生“正式总额与明细合计关系”的展示问题，需在报价阶段前确认。
- JWT 每请求读取实时账号状态；数据库不可用时认证不能继续。阶段 2 登录与生命周期规则见 D-018。
- PostgreSQL 任务表与价格库共享数据库，需要用指标防止 Worker 或批量导入影响在线请求。

## 阶段5模块与事务

document负责案件分类/角色/版本/幂等/审计，integration.storage依赖ObjectStorageService并由MinioObjectStorage实际存取。数据库锁住案件串行化单类有效计数、替换和提交；对象成功但数据库回滚时补偿未提交对象（历史对象不删除）。无分布式事务、失败补偿可能需要人工核对。

ocr任务表通过SKIP LOCKED+有限租约并发领取；过期令牌不能写回。OcrTaskStore单独事务领取/完成，Worker校验源哈希后调用可替换OcrProvider。完成写回先锁案件检查只读状态，人工复核及审计同事务；确认记录引用不可变快照。异步失败的错误码不包含源内容或凭据。

MapProvider本轮Mock，不真实定位；CS端接真实区域网点筛选与合成地图数据。所有新增路由默认鉴权，业务服务重新执行案件/角色/字段权限。阶段8通知/导出尚未实现，不存在新增旁路。

## 第6阶段 quotation 模块

新增quotation/{api,application,domain,infrastructure}及MyBatis XML，继续模块化单体。QuoteCalculator集中BigDecimal/BigInteger分计算与最大余数分摊，RepairAuthorizationGate只判断四项证据。QuotationService负责角色字段过滤、不可变快照、幂等、历史和开修；QuotationLifecycle与现有FileService同事务共享案件行锁，将核损材料变化与确认撤销绑定。复用WorkOrderMapper CAS和状态历史、AuditService及私有MinIO，不直接暴露表或对象存储键。

V7追加不可变原始/正式/核损/确认/事件/幂等表及可更新上下文，V1—V6不改。管理员只读、客服财务操作、当前网点原始报价/开修，OWNER拒绝报价接口。导出明确对外字段名单，不输出内部金额。两前端详情的QuotationPanel仅做当前阶段验证，金额保留字符串。

Windows既有target目录清理被拒绝时，可用validation.build.directory激活isolated-validation-build profile；Verify-Baseline与Start-Local限制路径在第二阶段local-validation内。仍执行完整clean verify，不跳过测试、迁移或构建。

## 第7阶段维修模块（部分实现）

repair领域API/application/domain/infrastructure复用workorder锁和CAS、quotation四项授权与开修事件、document私有附件以及audit不可变日志。独立repair_context版本控制进度/完工；不可变完工记录和文件版本关联保护证据，文件服务通过RepairMaterialPolicy检查冻结。复杂身份/分页查询使用MyBatis XML。事务命令锁避免同操作者同键跨案件并发重复执行。没有新微服务或外部接入；收车/投诉待规则确认。

第7阶段补齐V9/V10与complaint领域。repair统一案件行锁/CAS/事务命令锁控制收车、撤回与评价并保留原评价；complaint采用独立行锁/CAS与追加事件，复用FileAccess执行附件/案件/角色范围；内部说明在服务DTO构造时过滤。读取稳定分页，不耦合资金，不拆微服务。

## 第8阶段模块与事务边界

新增funds与notification领域，保持模块化单体。资金命令在案件行锁、独立context CAS及幂等/流水号事务锁下执行；目标、流水、冲销、审计原子落库。导入源文件统一ObjectStorageService私有MinIO存储、SHA256元数据，数据库回滚仅补偿本次未提交对象；不公开桶。CSV/XLSX内存解析，输入有界，预览编号批量匹配和500行分块写入；确认每行独立事务，错误不回滚其他行。

V12审计触发器同事务生成notification_event。Worker用FOR UPDATE SKIP LOCKED有界领取50事件，唯一键防重复投影；崩溃事务回滚后可恢复，不引入消息队列。个人通知读取重验角色和当前业务范围，固定安全消息不传播内部审计文本。待办基于正式业务状态SQL查询；deadline有独立CAS与历史，修改时锁案件/必要投诉记录并复核仍有效。

资金权限入口与字段输出均服务端执行；网点PAY查询限定当前派单，车主403，导入批次创建人限定。通知scope独立检查，导出私有no-store并防CSV公式注入。短信仅SmsProvider/DisabledSmsProvider，自动超时/重复/升级均关闭，无真实外部连接。
