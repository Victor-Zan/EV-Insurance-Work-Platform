# 业务流程与阶段路线

## 1. 文档用途

本文记录平台正常流程、异常状态流和提示词 1—13 的开发门禁。需求字段与权限以 `REQUIREMENTS.md` 为准，数据定义以 `DATA_DICTIONARY.md` 为准，尚未确认的业务规则只写入 `OPEN_QUESTIONS.md`，不得静默实现。

每个提示词都遵循同一门禁：确认本阶段未决事项 → 只实现本阶段 → 运行相关测试、lint、类型检查、构建和迁移验证 → 更新 `PROGRESS.md` → 汇报并停止。未经用户确认不得进入下一提示词。

## 2. MVP 正常业务流

```mermaid
flowchart LR
  A[客服草稿] --> B[正式建单与重复检查]
  B --> C[派单]
  C --> D[网点接单]
  D --> E[车辆到店]
  E --> F[上传材料]
  F --> G[Mock OCR]
  G --> H[人工确认]
  H --> I[网点原始报价]
  I --> J[客服审核与总额加价]
  J --> K[平台正式报价]
  K --> L[录入最终核损金额]
  L --> M[上传核损单]
  M --> N[保险确认 + 客服确认]
  N --> O[维修授权]
  O --> P[维修与进度]
  P --> Q[必传完工照片]
  Q --> R[车主确认收车]
  R --> S[评价或投诉]
  S --> T[保险回款记录]
  T --> U[网点结算记录]
  U --> V[完成]
```

维修授权必须同时满足：核损单已上传、最终核损金额已录入、保险确认已记录、客服完成平台确认。平台只记录“保险公司 → 平台 → 维修网点”的资金状态，不执行真实付款。

## 3. 阶段 4 正常状态流

```mermaid
stateDiagram-v2
  [*] --> DRAFT
  DRAFT --> PENDING_DISPATCH: 正式提交 / 生成业务编号
  PENDING_DISPATCH --> PENDING_ACCEPTANCE: 派单 / 新 assignment_version
  PENDING_ACCEPTANCE --> PENDING_ARRIVAL: 当前网点接单
  PENDING_ARRIVAL --> ARRIVED: 当前网点确认到店
```

- 草稿只有创建客服和管理员可见，可修改、物理删除，不生成业务编号，也不能派单或进入正式待办。
- 正式提交后不能退回草稿，正式工单不能物理删除。
- 每次派单生成新 `assignment_version`；旧版本不能操作当前工单。

## 4. 阶段 4 异常状态流

```mermaid
stateDiagram-v2
  PENDING_ACCEPTANCE --> PENDING_DISPATCH: 网点拒单 / 取消派单
  PENDING_ACCEPTANCE --> PENDING_ACCEPTANCE: 改派 / 新版本
  PENDING_ARRIVAL --> PENDING_DISPATCH: 取消派单
  PENDING_ARRIVAL --> PENDING_ACCEPTANCE: 确认未到店后改派
  PENDING_ARRIVAL --> ARRIVAL_EXCEPTION: 标记到店异常
  ARRIVAL_EXCEPTION --> PENDING_ARRIVAL: 继续等待
  ARRIVAL_EXCEPTION --> PENDING_DISPATCH: 取消派单
  ARRIVAL_EXCEPTION --> PENDING_ACCEPTANCE: 确认未到店后改派
  ARRIVED --> PENDING_ACCEPTANCE: 管理员异常改派 + 转运说明
  PENDING_DISPATCH --> CANCELLED: 取消整个工单
  PENDING_ACCEPTANCE --> CANCELLED: 取消整个工单
  PENDING_ARRIVAL --> CANCELLED: 取消整个工单
  ARRIVAL_EXCEPTION --> CANCELLED: 取消整个工单
  ARRIVED --> CANCELLED: 仅管理员
```

异常规则：

- 拒单、取消派单、改派、标记到店异常、取消整个工单和关键字段修改都必须填写原因。
- 到店异常可继续等待、取消派单、改派或取消整个工单；系统不自动改变状态。
- 已到店或已产生报价后，只允许管理员取消整个工单。
- 取消必须记录说明以及是否通知车主、网点；当前阶段只记录通知意图，不提前实现站内通知。
- 不提供通用“回退上一状态”。

## 5. 重复、并发与权限流程

正式提交前先串行执行重复检查：

1. 保险公司 + 报案号完全相同属于强重复，数据库唯一约束兜底，禁止创建并返回已有工单号。
2. 同 VIN + 相近事故时间、同手机号 + 同车辆 + 相近事故时间、同保单号 + 同车辆属于建单疑似重复。
3. 同车主 + 同目标网点 + 短期重复属于派单疑似重复。
4. 相近/短期默认 7 天，由管理员配置；疑似重复仅警告，继续操作必须填写原因并审计。

所有状态操作带 `Idempotency-Key`，同时校验工单 `version` 和当前 `assignment_version`。相同键返回第一次响应；重复接单和重复到店在同网点、同派单版本下语义成功，不重复生成状态历史、审计或派单。

服务端数据范围：管理员全部；客服只看本人草稿及全部正式工单；网点只看当前指派给本店的工单；车主只看绑定本人的工单。列表和详情分别应用字段脱敏，不依赖前端隐藏。

## 阶段5材料与候选复核（2026-10-09）

附件在当前案件与派单范围下上传，客服可补传/替换/作废；旧版不覆盖、仅内部可读。绑定车主仅三类照片，网点仅本次派单自己的报价和照片。通知单缺失原因由客服追加，后补文件改变已齐状态但保留历史原因。

OCR创建→QUEUED→租约RUNNING→SUCCEEDED候选或FAILED；失败在次数上限内可重试，过期租约可恢复。客服修正产生新快照，确认引用当前版本；修改后旧确认不确认新版本。此流程不改变正式案件/报价状态。

COMPLETED/CANCELLED为本阶段只读终态：禁止材料和OCR人工变更，后台领取及完成写回也检查终态。只读不是重开授权；阶段6以后相关修订/开修门禁另确认。

## 第6阶段报价与授权状态流（D-032）

当前已接网点到店后提交原始版，进入QUOTE_REVIEWING；客服审核加价生成正式版进入WAITING_INSURER_ASSESSMENT；客服录入最终核损进入WAITING_REPAIR_AUTHORIZATION。客服代录保司及客服确认，四项齐备时记录授权；当前网点调用开修API，在同事务重新验证四项后进入REPAIRING。

开修前原始/正式报价、核损金额或有效核损材料集合变化，撤销授权并使两确认全部失效；历史不覆盖。网点不二次确认，回款不构成门槛。开修后禁止常规报价/核损及相关材料变更，异常修订延期；完成取消只读。四项证据独立于报价流程状态，不增设第五项报价门槛。阶段4改派/取消范围保持不变，报价进入审核后不额外放开改派；报价权限持续检查当前派单版本。

OWNER不参与报价/费用。原始单价仅网点新版本可改，客服只调整总额；正式外部明细按占比分摊，合计精确，行金额为准。接口和验收见PHASE6_API.md / PHASE6_VERIFICATION.md。

## 第7阶段当前已实现范围（D-035）

合法四项门禁开修后，当前已接网点在REPAIRING追加进度及可选有效进度照片；进度不修改状态起始时间。完工须提交至少1张当前网点本次派单实际上传的有效JPG/PNG完工照；同事务冻结其版本快照、写状态历史/审计，进入WAITING_OWNER_CONFIRMATION。完工证据以后不得替换或作废。并发完工和照片作废共用案件锁，不能出现已提交但证据已作废的结果。

用户已修改收车意向为车主或客服确认后COMPLETED、客服可撤回、评价和评分非必填；客服代操作范围、撤回目标/已有评价和投诉规则待答复，尚不开放相应写接口。不自动确认或进入阶段8。

## 第7阶段最终流程（D-037，替代前述待确认描述）

REPAIRING由当前网点或客服代录进度/提交完工，仍须原授权及网点本次派单上传的照片。完工→WAITING_OWNER_CONFIRMATION；绑定车主或客服确认收车→COMPLETED；评价/评分非必填，资金阶段8独立，不引入OWNER_RECEIVED。

仅客服可有原因撤回已收车→WAITING_OWNER_CONFIRMATION；原完工照片保持冻结，原评价留历史且不计当前评分。再次收车后车主不重复评价，客服通过追加纠正版进行复核，不覆盖车主原评价。完成后材料/报价/维修进度仍只读；客服收车撤回、可选评价及独立投诉为D-037明确例外，不扩展为全表可写。

车主开修后可创建独立投诉，完成后也可提交，取消后不新增；车主提交后不能改。管理员按SUBMITTED→PROCESSING→RESOLVED→CLOSED处理；客服追加纠正说明。网点仅当前派单相关公开内容；内部说明仅管理员/客服。投诉不改变维修状态或评分；无自动SLA、返工、重开、发短信或付款。

## 第8阶段资金与待办状态流

资金context与维修context独立。客服追加RECEIVE/PAY目标版本，目标未知UNSET、已定但未收付UNPAID、部分PARTIAL、净流水等目标SETTLED（零目标/零净值即SETTLED）。分笔记账不改维修状态；冲销新增关联，原流水和编号保留。PAY必须实际收车完成、当前应付已定和保险回款SETTLED；撤回收车保留财务历史，重收车前禁止新增实付。完成后的资金操作是D-038明确例外；取消仅冲销、不改目标或新增收付。

导入：上传真实私有源文件→有界批量匹配→READY/NEEDS_REVIEW/INVALID→客服有原因纠正冲突→逐行确认RECORDED/DUPLICATE/FAILED。每行独立事务且方向＋流水号全局去重，重复确认不会重记；不一致双编号不自动猜案件。

通知由同事务审计事件outbox→并发Worker领取→个人通知，已读逐人记录；每次查询重验角色/车主绑定/当前派单。待办直接来自业务状态，旧阶段处理或改派后失效。客服设置/修改/清除deadline只更新独立待办期限和历史，不改案件或资金；过期显示标签，自动超时、重复提醒、升级和真实短信均关闭。
